## 0. 一句话

**句式的味已经洗掉了，剩下的味是"没有真东西"。** 所以这一轮干的事是：
先把机器留下的节奏痕迹清干净（可自动化、可复跑、可验证），
再把证据、立场、版本时效、勘误责任**放回书里**（半自动 + 人工闸门）。

### 1.1 改造前的实测基线（120 章）

| 指标 | 中位数 | 目标 | 判定 |
| --- | --- | --- | --- |
| 章长变异系数 CV | **0.0729** | > 0.25 | 整齐得刺眼——120 章几乎等长 |
| 破折号密度 | **5.56 /千字** | 越低越好 | 第一重灾区（全书 22074 处） |
| 修辞套路密度 | 2.05 /千字 | ≤ 1 | "不是X，而是Y" 512 处 |
| 极短句占比 | 2.0% | > 3% | 句子长度过于集中 |
| 具体性密度 | **1.09 /千字** | ≥ 8 | 最大的洞：写的是"空"，不是"错" |
| 直引语密度 | 7.78 /千字 | ≥ 0.5 | 达标 |
| 段首去重率 | 61.6% | > 70% | 段首开头重复 |
| 黑名单密度 | 0.0 /万字 | ≤ 3 | 词表其实很干净 |

> **一处必须写下来的检测器 bug**：第一版检测器的直引语指标只认中文弯引号 `“ ”`，
> 而本仓库源稿全书用 ASCII 双引号 `"`（11 万+ 处），于是指标 7 一律读成 0.00，
> 看起来像"全书没有一句真人原话"。**实际上有 29921 处。**
> 修好检测器后重打基线，才有了这张表。基线必须用同一版检测器打，否则对比不成立。

**关键判断**：黑名单词其实很少（0.0 个/万字），AI 味**不在词表上**，
在**结构工整 + 抽象空洞 + 没有人味素材**这三件事上。
所以本轮的主要战场是第二层和第三层，不是换词。

### 1.2 Goodhart 防御（写进了脚本注释）

> 检测器只用于**找最差的章**，不用于验收。
> 一旦变成 CI 门禁，写作会开始为指标优化，产出"分数全绿但一股机灵假味"的文本。
> **听诊器，不是法官。**

## 2. 第一层：文本手术（全库 120 章 + 17 篇导语）

`scripts/voice_lint.py --fix`。每条规则挂 ID，触发量写进 `state/voice_report.json`。
默认 dry-run，结构校验不过就不写回。

| 规则 | 实测命中 | 做法 |
| --- | --- | --- |
| **S4 破折号降频** | **15734** | `——` → `，`(62%) / `：`(20%) / 保留(18%)。问号叹号后的破折号不动（避免造出 `？"。`） |
| **S6a 列表收尾统一** | **2616** | 19.7% 的列表项以「；」收尾——机器生成的铁证，统一改「。」 |
| **S2 "不是X而是Y" 降频** | 313 | 保留 1/3，其余拆成两句、去掉"而"这个公式信号 |
| **S5 问句配额** | 100 | 每章最多留 2 个反问句，其余改陈述 |
| **S1 拆三连排比** | 58 | `A；B；C。` → `A，B。C。`；只认全角分号 |
| **S3 删段尾总结句** | **0** | **真阴性**：全书 58 段含收束词，但没有一段收在段尾。规则留着，不硬凑 |
| **W 黑名单** | 98 | S 级删、A 级换口语、B 级只标记进人工队列 |

### 2.1 两处真实踩坑（已修，值得记下来）

1. **半角 `;` 被当成中文分号**：HTML 实体 `&lt;` `&gt;` 结尾都是 `;`，
   S1 的正则把 `Response&lt;WeatherResponse&gt;` 拆成了两半。
   → 正则只认全角「；」，并且把 HTML 实体加进保护表。
2. **S3 的"可见"撞上"onStart 可见"**：段尾总结句规则把 `onStart 可见、onResume 可交互`
   当成收束句删掉了前半句。→ S3 改成只看**段尾**，并从词表里去掉"可见"。

### 2.2 效果

| 指标 | 术前 | 术后 | 变化 |
| --- | --- | --- | --- |
| 破折号密度 | 5.56 /千字 | **1.53 /千字** | −72% |
| 全书破折号总数 | 22074 | 6375 | −15699 |

## 4. 第二层：证据注入

### 4.1 版本锚点（80 章）

`scripts/inject_version_anchor.py`。只给**确有操作路径**的章加——
纯概念章（编程思维、AI 原理）加"本章界面路径按 iOS 18.x 核对"是假话。

> 本章界面路径按 iOS 18.x / HarmonyOS 5.x / Android 15 核对（2026 年 11 月）。
> 你的机型或系统版本不同，菜单名字和位置可能对不上——以你手机上显示的为准。

**措辞规则**：说"核对"、标日期，不写"实测"——全书没做逐台设备的实机复测，
写"实测"是本书最不该出现的一类假话。

### 4.2 路径库（单一真源）

| 文件 | 作用 |
| --- | --- |
| `path_db.json` | 136 条路径，覆盖 36 章。由 `scripts/build_path_db.py` **从源稿生成**，不是手抄的表 |
| `scripts/path_check.py` | 巡检：字段完整性 / 锚点章登记率 / 过期复查提醒 / 路径是否还在正文里 |

巡检报告如实区分两种情况：**有箭头链但没登记**（要补）与
**散文式路径**（47 章用散文描述操作，不计漏登记）。诚实报覆盖率，不粉饰。

### 4.3 案例框与立场框

**最终注入量**（44 个章有证据块）：

| 类型 | 数量 | 完整性 |
| --- | --- | --- |
| 案例框 `<div class="case-box">` | **105** | 105/105 有 head + quote + **src 来源标注** |
| 立场框 `<div class="stance-box">` | **49** | 49/49 有 head + **note 利益声明** |
| 版本锚点 `<div class="version-anchor">` | **92** | 87 条统一文案 + 5 条按章定制（平台后台类章节不写手机版本号，写版本号会是假话） |

- **案例框**：有具体细节、有后果、有解法、引号里是真实的人话。
- **立场框**：明确结论 + 理由 ≤ 3 条 + 利益声明。和稀泥是 AI 最深的味。

**来源分级是硬约束**：没有真人素材时一律写 `场景来源：全书通用场景（非特定读者）`。
一个编出来的"真实案例"比 353 万字工整的 AI 味更危险——它伤的是信任。
已按此红线清理过正文里的虚构读者名（"小马""小周""老王""小明"→"同事""一位读者""某人"）。

## 9. 回归门禁

一条命令跑完（`scripts/deai_gate.py`，10/10 全绿）：

```bash
py -3 scripts/deai_gate.py
```

分项：

```bash
py -3 -m bookkit build --book source/v1.9/book.json --verify   # 逐章等价
py -3 -m bookkit lint                                           # 结构/锚点/目录
py -3 -m bookkit check --claims --index                         # 宣称值与死链
py -3 scripts/html_audit.py                                     # HTML 全量审计
py -3 scripts/deai_check.py --dir source/v1.9/chapters          # 单章体检
py -3 scripts/path_check.py                                     # 路径库巡检
py -3 -m bookkit split --book source/v1.9/book.json --strict-budget
py -3 -m pytest tests/ -q                                      # 47 项单测
```

**手术没有把排版改坏**——`build --verify` 的 120/120 逐章等价是这一轮的安全网。

## 11. 先说一个反直觉的发现

| 指标 | v1.8（改造前） | v1.9（改造前） | 说明 |

| 修辞套路 /千字 | **0.35** | 2.05 | v1.9 明显更"工整" |

| 章长 CV | **0.61** | 0.073 | v1.8 长度参差，v1.9 整齐得刺眼 |

**AI 味是 v1.9 的"扩写至 29K+/章"那一阶段带进来的**，不是这本书的底色。
v1.8 那 84 章是更早写的，也更像人写的。

2. v1.8 的**朗读问题点只有 145 处**（v1.9 是 2290 处），说明它的句子本身读得顺。

## 14. 朗读测试（方案 §6.3）

详见 **[docs/deai/READ_ALOUD.md](READ_ALOUD.md)**。要点：

- **三项信号做成了可检测的**（`scripts/voice_read_test.py`）：喘不上气 / 拗口 / 听了走神。
- **阈值按每种语言自身的分布定**，不是拍脑袋：实测全书每种语言"无标点连续段"
  长度的 P99.5，超过它才是该语言里读起来真的别扭的少数句子。
- **1716 章**（v1.9 120 + v1.8 84 + 18 语 1512）逐章人工朗读不是一次会话能做完的，
  所以做法是"机器标出可疑处 → 逐条改 → 改完复测"，**改不动的如实留在清单上**。
- **一处机械修复被否决并记录在案**：把「A → B → C → D → E」批量改成编号列表，
  在本书实测下来 4 处候选**全部不安全**（路径链嵌在句中、拆开会甩掉正文、章节导航表不该拆），
  相关工具已删除，不留在仓库里当陷阱。方案 §6.3 说的"人的语感是终点裁判"，
  在流程箭头这件事上表现得最具体。

## 14.1 顺带挖出来的一个大坑：译文的"伪标题"

做对齐体检时发现了一件事，**比去味本身更重要**。

### 现象

v1.8 的 18 种译文里，大量章节的"小节标题"**根本不是标题，是被提成标题的正文句子**。
英文第 9 章（中文：移动办公与学习）在源稿里长这样：

```
#### : If your company uses genuine Office, this is the best choice. Format compatibility …
```

一百多个字符的句子，顶着 `<h4>` 的粗体大标题。原因是反解时
`<li><strong>Microsoft 365</strong>：如果你公司用正版Office…</li>`
被拆成了「`#### ` + 丢掉标签的正文」，标签（「Microsoft 365」）则变成章里孤零零的一行。

**量化**：44% 的译文章节（702 / 1596）里，章的小节大纲是一串大写粗体句子。
中文（及其繁体/粤语/文言三个版本）**零**——说明是反解环节引入的，不是翻译质量问题。

### 为什么现有门禁没拦住

仓库的门禁只验「源稿 → HTML」和「HTML → 源稿」的**往返**。
往返是自洽的：**错的译文重建出来还是错的译文**。所以这类损坏能一路活到发布。

### 做了两件事

1. **修掉看得见的破损**（`scripts/fix_i18n_pseudo_headings.py`）：
   `#### : 正文` → 列表项；`#### 超长正文`（> 60 字符）→ 普通段落；
   顺带修掉反解造成的**标题文字重复**。
   **702 章 → 5 章（0.3%）**，共修 1605 处。
2. **加一道新门禁**（`scripts/i18n_align_check.py`）：
   按 `####` 小节切块，比较「每块字符数」这个**形状向量**与中文的相关系数。
   译文与中文的章节结构是一一对应的，形状应当高度相关；相关性掉下来就是这一章串稿了。
   现在报告 **731 处待处理**，逐章可查。

### 还没修的，以及为什么

译文**真正的小节标题在反解时就丢了**（中文有 461 个 `####`，
英文修完后只剩 349 个、希腊文 324 个、韩文 395 个）。
这是**内容修复**，不是去味：要按中文的章节结构把标题**重新翻译**回去。
仓库里已有现成的机器：`bookkit tm`（翻译记忆库）能报出"哪些中文段落在译文里缺失"。

**这一条建议作者决定**：是接受"译文没有小节大纲"（阅读体验差但结构干净），
还是排一轮重译把标题补回去（工作量大但结构对齐）。
在补回去之前，译文页面上会出现"某些章没有小节标题"的情况——
这是已知状态，不是新引入的。

## 16. 三条建议（给作者）

1. **先采素材，再谈指标。** 案例框、立场框的框架已经就位，
   但 105 个案例框里没有一个是"群友原话"。下一轮最有价值的动作是：
   每周翻一次 QQ 群，采 3–5 条带细节的真实问题（原话保留方言和不完整句），
   按 `evidence_spec.md` 的来源分级归档。这一件事的收益，大过再跑十轮文本手术。
2. **健康篇尽快找一位审校人。** 本版已经把表述收紧、加了免责声明，
   但"收紧"不等于"审校"。署名之前，这一篇请当参考。
3. **路径库需要有人负责。** 现在它是从源稿生成的，生成得出来不等于有人维护。
   每年 iOS / 鸿蒙 / 安卓大版本后跑一次 `path_check.py`，
   把 `needs-confirm` 的条目复查一遍——这件事有人做，路径库才是活的。
