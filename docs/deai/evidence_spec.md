> 所有改稿者（人或 AI）都必须照它写，保证全书体例一致。

## 0. 为什么是这一层

第一层文本手术解决的是**节奏**：破折号密度、"不是X而是Y"、列表收尾、章标题模板。
这些做完，全书读起来不再像机器排版，但**仍然是空的**——

- 具体性密度：全书每千字 1.09 处（目标 ≥ 8）
- 直引语密度：全书每千字 0.00 处（目标 ≥ 0.5）

方案 §11.3 讲得很直白：**替换率 > 润色率**。读者闻的是证据的味，不是句子的味。
这一层就是往正文里放真东西。

## 1. 版本锚点（每章一条，靠近章节开头）

放在章节 `chapter-intro` 之后、正文第一节之前：

```html
<div class="version-anchor">本章界面路径按 iOS 18.x / HarmonyOS 5.x / Android 15 核对（2026 年 11 月）。你的机型或系统版本不同，菜单名字和位置可能对不上——以你手机上显示的为准。</div>
```

**措辞规则**：

- ✅ 说"核对"、说"按……核对"、说"2026 年 11 月"——这是**时效声明**。
- ❌ 不许写"实测"两个字，除非那台设备真的有人拿着按过。写"实测"而没人实测，是本书最不该出现的一类假话。
- ✅ 必须写"以你手机上显示的为准"——把判断权交回读者。
- 不同平台差异大的章节，iOS 专属或安卓专属的，用对应的那一套版本号。

## 2. 案例框（Case Box）

案例框的用途是**把抽象操作变成一个具体场景**。必须满足：

1. **有具体细节**：机型、系统版本、容量、时间、金额，至少两个。
2. **有后果**：不这么做会怎样。
3. **有解法**：怎么办。
4. **引号里是真实的人话**（系统提示原文、App 弹窗原文、读者原话）。

```html
<div class="case-box">
<div class="case-box-head">翻车现场</div>
<p>存储还剩 4 个 G，微信却提示"存储空间不足"。这类提示指的是<strong>手机内部存储</strong>，不是微信自己那点空间。</p>
<p class="case-box-quote">"存储空间不足，无法继续下载"</p>
<p class="case-box-src">场景来源：全书通用场景（非特定读者）</p>
<p><strong>怎么办</strong>：【设置】→【存储】看总数，别去微信里找。腾出 10 个 G 再说。</p>
</div>
```

### 案例框的**来源分级**（必须如实标注，不得冒充）

| `case-box-src` 写法 | 含义 | 能不能用 |
| --- | --- | --- |
| `场景来源：全书通用场景（非特定读者）` | 由通用故障现象改写的教学场景 | ✅ 默认用这个 |
| `场景来源：读者群 1074995524（2026-W47，已获当事人同意，化名"叶子"）` | 真实读者案例 | ⚠️ **只有真有其事才能用**。没有原始素材就写"通用场景" |
| `场景来源：系统提示原文（iOS 18.3）` | 系统/App 的原始文案 | ✅ 可用，但必须是真实文案 |
| `场景来源：作者实机操作记录（2026-11）` | 作者本人操作过 | ⚠️ 需要真实记录支撑 |

**红线**：**禁止虚构读者姓名、群聊记录、新闻事件、日期、金额、机型**。
一个编出来的"真实案例"比 353 万字工整的 AI 味更危险——它伤的是信任。

## 3. 立场框（Stance Box）

用在"对比 / 推荐 / 该不该装 XX"类章节。三要素齐全才算合格：

1. **明确结论**（不是"各有优劣"）
2. **理由不超过 3 条**
3. **利益声明**

```html
<div class="stance-box">
<div class="stance-box-head">作者立场</div>
<p>我劝你别装任何"清理大师"类 App。理由：</p>
<ul>
<li>它干的活，相册自带的功能就有；</li>
<li>常驻后台，白耗电；</li>
<li>部分版本会诱导付费。</li>
</ul>
<p class="stance-box-note">（无利益相关。某款清理大师我付费用过两年，结论是卸载了。）</p>
</div>
```

**利益声明怎么写**：如果作者没用过，就在括号里明说"没用过，以下是机制上的判断"。
**不要编造使用经历**。

## 4. 路径库（path_db.json）

正文里每条操作路径，在 `path_db.json` 里登记一条：

```json
{
  "chapter": 22,
  "file": "22-di-shi-jiu-zhang.md",
  "task": "误删照片恢复",
  "path": ["相册", "最近删除", "选择", "恢复"],
  "platform": "iOS",
  "version_scope": "iOS 18.x",
  "status": "confirmed",
  "date": "2026-11",
  "note": "最近删除保留 30 天；鸿蒙在「图库 → 最近删除」"
}
```

- `status`：`confirmed`（路径稳定/官方文档明确）/ `needs-confirm`（版本敏感，需复查）。
- `date`：路径最后核对的年月。**不要写你没做过的核对日期。**
- `version_scope`：这条路径在哪个版本区间成立。

`scripts/path_check.py` 会做三件事：
1. 查 `path_db.json` 里有没有 `verified_on`/`date` 空值；
2. 查正文里提到但库里没登记的章；
3. 查标了 `needs-confirm` 且已过期的条目（供每年大版本后巡检）。

## 5. 免责声明（健康篇必备）

健康类章节（心率、血氧、睡眠、女性健康、运动）**每章末尾**必须有：

```html
<div class="callout-box warning-box">
<p><strong>本篇不能替代医嘱。</strong>手机和手表测的是趋势，不是诊断。指标异常、持续不适，请就医。</p>
</div>
```

写"本篇不能替代医嘱"，不要写"仅供参考"——后者太软，读者会当成免责套话继续当诊断用。

## 6. 落位规则

- **版本锚点**：章节开头，`chapter-intro` 之后。
- **案例框**：放在它解释的那个操作**之前**（读者先看到场景，再看步骤），或放在该小节末尾作为小结。
- **立场框**：放在该小节的结论位置，不要打断步骤叙述。
- 每章**至少 1 个**证据块（版本锚点算半个），关键章 2–3 个。
- 不要为凑数硬塞。案例框必须是**这个章真正会发生的事**。
