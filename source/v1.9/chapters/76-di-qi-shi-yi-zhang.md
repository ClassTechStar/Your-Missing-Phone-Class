### 第七十一章：搭建开发环境——DevEco Studio 与第一个项目

{class="chapter-intro mb-4"}
工欲善其事，必先利其器。这一章咱们装好 DevEco Studio、跑通第一个鸿蒙应用，就像第 50 章（安卓）和第 60 章（iOS）做过的一样。好消息：DevEco 的安装比 Android Studio 简单（不用管模拟器加速），比 Xcode 门槛低（不需要 Mac）。

在动手之前，先给三个"读者画像"对号入座。第一种：你刚学完第 37-47 章的 AI 编程，想看看鸿蒙生态里 AI 工具链长什么样，这一章的环境搭建对你来说就是"换个 IDE"的事，核心概念全部通用。第二种：你是有经验的安卓或 iOS 开发者，来评估鸿蒙值不值得投入：本章的目录对照表和"三平台对照"注脚会帮你最快建立映射。第三种：你是纯新手，前面开发篇还没读，没关系，本章的每一步都写得足够细，跟着做就能跑通；但建议把第 48 章或第 59 章先翻一遍，理解"环境搭建"这件事在移动开发里的通用套路。

还有一个时间成本的预告：从零到"第一个应用跑起来"，正常节奏是一到两个小时（含下载时间）。如果你卡在某个报错上超过半小时，先去本章末尾的"常见坑"清单对照：你遇到的问题九成已经写在里面了。

::: div .quick-read
##### 本章速读（5 分钟版）
这一章把"厨房"搭好：装好 DevEco Studio、跑通你的第一个鸿蒙应用。好消息是鸿蒙环境堪称三大平台里最友好的一条：不用 Mac（Windows 就能完整开发）、不用折腾模拟器加速、SDK 随 IDE 预置、调试签名自动办。从零到"第一个应用跑起来"，正常节奏一到两个小时。
最关键的有三件事。第一，<strong>安装时避开三个雷</strong>：磁盘留 20GB 以上（IDE 本体加 SDK、模拟器镜像、构建缓存，40GB 才从容）；SDK、IDE、项目目录全用纯英文路径，别带中文和空格；Node.js 让 DevEco 用它内置推荐的版本，全局 Node 版本对不上是新手第一大报错来源。第二，<strong>建项目认准四个选项</strong>：Empty Ability 空模板、Stage 应用模型（老的 FA 模型已淘汰别选）、bundle name 当成应用身份证（上架后不可改，com.example.hello 只能学习期用）、Compile SDK 选默认最新。第三，<strong>三种"看见应用"各管一摊</strong>：预览器秒级刷新、只渲染界面（日常写 UI 的效率之王）；模拟器是完整系统（测通知、测分布式，双开两台还能模拟流转协同，内存 16GB 以上再玩双开）；真机是最终真相（性能、传感器只有它诚实），连真机记得在"关于手机"里连点版本号七次开开发者模式、开 USB 调试，那道授权弹窗几秒不点就自己消失，错过就重插线。
今天就能做的最小动作：建一个 HelloHarmonyOS 项目，把页面里的 message 改成你的名字，看预览器秒级刷新，再点一下按钮看文字变化：状态驱动界面的体验，从这一刻就是你的了。
最大的坑，本章备好了一份十二个常见报错的"症状→根因→解法"手册（Node 版本、中文路径、模拟器启动失败、设备列表为空）。Install Failed、预览器白屏、端口占用、系统时间不对这些也在里面，撞上了先回来对号入座。卡住超过半小时就走"自救三步"：复制报错原文加版本号去搜（别搜"装不上怎么办"）→ 查官方发布说明和变更日志 → 按"环境、完整报错、复现步骤、已尝试"四要素去社区提问。再送两句：模拟器闹"灵异"先冷启动（丢弃快照），别上来就删镜像；AI 生成的代码别整段粘贴不求甚解：AI 能替你写代码，不能替你理解报错。
##### 速查表
- 安装三注意：磁盘留 20GB 以上、路径全纯英文、Node 用 DevEco 内置推荐版
- 建项目四选：Empty Ability、Stage 模型（别选 FA）、bundle name 当身份、SDK 默认最新
- 三种看应用：预览器秒刷只管 UI、模拟器测系统能力、真机是最终真相
- 真机三步：连点版本号七次开开发者模式 → 开 USB 调试 → 授权弹窗别错过
- 升级对齐：命令行工具升同版本、API Change Assistant 查变更、新旧设备都测
- 报错三步自救：报错原文+版本号去搜 → 查官方发布说明 → 四要素模板提问
- 签名省心法：调试勾自动签名即可，过期报错就取消重勾重新生成
- 环境体检八项：IDE、SDK、账号、预览器。模拟器、真机、日志、磁盘，全绿再开工
:::

#### 一、下载与安装 DevEco Studio

去华为开发者官网（developer.huawei.com）→ [开发] → [鸿蒙] → [工具]，下载 DevEco Studio for Windows（或 Mac）。安装过程一路下一步，唯一要注意的是<strong>磁盘位置</strong>：SDK + 模拟器 + 构建缓存加起来要 20GB 以上的空间，别塞进快满的 C 盘。

磁盘规划多说一句：IDE 本体约 3-5GB，SDK 组件按需下载（ArkTS、ArkUI、预览器是必装项），模拟器镜像每个 5-8GB，再加上 Gradle/Hvigor 的构建缓存和项目文件，一个"能日常开发"的环境，20GB 是底线，40GB 才从容。如果你的 C 盘空间紧张，安装向导里把 SDK 和缓存路径改到其他盘；改了路径记得记住它，后面排查问题时"SDK 到底在哪"是个高频疑问。

下载时还有个选择：标准版 vs 命令行工具版。日常开发选标准版（带完整 IDE）；如果你只是要在 CI 服务器上做构建（第 45 章的自动化流水线场景），命令行工具包更轻量。本书主线用标准版。

首次启动会引导你完成三件事：<strong>同意协议</strong>、<strong>登录华为开发者账号</strong>（个人实名认证免费，后面真机调试和上架都要用）、<strong>配置 SDK</strong>（默认路径即可，也可自定义）。有个好消息：自 6.0.0(20) 起，DevEco Studio 已经预置了对应版本的 HarmonyOS SDK，重新构建时会自动使用，老教程里"单独下载 SDK"的步骤可以直接跳过。当前 IDE 版本方案也已随 API 走（最新为 DevEco Studio 26.0.0，另有鸿蒙电脑版）。装完建议再进 [Settings] → [DevEco Studio] 检查一次 SDK 组件：ArkTS、ArkUI、预览器默认都会装上。

开发者账号这一步多说两句：个人实名认证只需要身份证信息和人脸识别，几分钟完成，免费。它和"发布应用"的账号是同一套：第 78 章上架时的账号就是现在登录的这个。所以现在认真注册，填的信息以后要一致。企业开发者略有不同（需要营业执照等材料），个人学习阶段用个人账号足够。

::: div .warning-box .rounded-lg .p-4 .mt-4
{class="font-semibold"}
<i class="fas fa-exclamation-triangle mr-2"></i>常见坑：Node.js 版本

{class="mt-1"}
DevEco 的构建工具链依赖特定版本的 Node.js。如果本机已装过 Node，建议让 DevEco 使用它内置推荐的版本（安装向导会提示），避免全局版本冲突，这是新手最常见的第一个报错来源。
:::

Node.js 的坑展开说一下原理：DevEco 的预览器和部分构建工具基于前端技术栈，依赖 Node 运行时。如果你本机是前端开发者，全局 Node 版本可能比 DevEco 需要的新很多，某些构建脚本的 API 在新版本里被移除了，就会报出一堆看不懂的错误。DevEco 的解法是"内置推荐版本"：安装向导会检测并提示你使用它自带的 Node，接受这个建议，让 DevEco 的工具链自成一体，不污染你的全局环境。如果你坚持用全局 Node（比如多个 IDE 共享），至少要用版本管理工具（如 nvm）为鸿蒙项目单独切版本。

安装完成的验证清单：启动 DevEco 无报错；[File] 菜单能正常打开；右下角的进度条（SDK 同步）跑完；登录账号后头像出现在右上角。四项都过，环境的第一步就稳了。

#### 二、创建第一个项目：Hello HarmonyOS

[File] / [New] / [Create Project] / 选 <strong>Application → Empty Ability</strong>（空模板，对应安卓的 Empty Activity / iOS 的 App 模板）。配置页里几个关键项：

- <strong>Project name</strong>：HelloHarmonyOS（项目名）
- <strong>Bundle name</strong>：com.example.hello（包名，上架前要换成自己的域名反写）
- <strong>Compile SDK</strong>：选默认的最新 API 版本。build-profile.json5 里 targetSdkVersion（目标）、compileSdkVersion（编译）、compatibleSdkVersion（最早兼容）三个字段各管一件事；想覆盖还没升级系统的老设备，就把 compatibleSdkVersion 显式写小，并确认用到的新 API 在老版本上有可用分支
- <strong>Model</strong>：Stage（应用模型，本书主线：老的 FA 模型已淘汰，别选）

模板选择多说两句：除了 Empty Ability，向导里还有带导航、带卡片的各种模板。新手选 Empty 的理由很实际，模板里预置的代码你还没能力看懂，空模板的代码量最小，每一行都在本章和接下来两章的解释范围内。等读完第 73、74 章，再回头看那些模板，你会发现它们就是"预置了好办法结构"的起点，到时候用才真正有吸收能力。

Bundle name（包名）值得专门强调：它是应用在鸿蒙世界的唯一身份证，上架后不可更改。com.example.hello 这种默认值只能在学习阶段用；将来上架时要用你自己的域名反写（比如你持有 myapp.cn，就写成 cn.myapp.xxx）。现在学习阶段不用纠结，但养成"包名 = 身份"的意识，第 78 章讲签名与上架时你会感谢它。

三个 SDK 字段的区别再用一个比喻：compileSdkVersion 是"你用什么教材学习"（用最新的 API 写代码），targetSdkVersion 是"你声明自己适配到哪个版本"（系统据此决定行为），compatibleSdkVersion 是"你承诺最低能照顾到哪个版本"（低于它的设备装不上）。三者通常"编译最新、目标最新或次新、兼容按需放宽"，这个策略在安卓（第 56 章）和 iOS（第 67 章）里逻辑相同，只是名字不同。

resources 目录里再展开一层：base 文件夹放默认资源，element 文件夹里的 string.json 存字符串：鸿蒙推荐"字符串全部资源化"（代码里用 $r('app.string.hello') 引用），这是为多语言和后期维护打的基础。第 79 章讲服务卡片时，资源化的好处会更明显：同一份字符串资源，卡片和主页面共用。

entry 这个词也解释一下：一个应用可以有多个"模块"（module），entry 是主模块（应用的入口），其余是功能模块（按需下载的特性模块，类似安卓的 Dynamic Feature）。学习阶段只用 entry 就够了，但知道"鸿蒙的应用结构是模块化的"，看官方文档时就不会迷失。

#### 三、跑起来：预览器、模拟器与真机

鸿蒙有三种"看见应用"的方式，开发体验各不相同：<strong>Previewer 预览器</strong>（秒级热刷新，不用装系统，改 UI 立刻可见）、<strong>Emulator 模拟器</strong>（完整系统镜像，能测分布式等系统能力）、<strong>真机</strong>（华为手机/平板，开 USB 调试后直连）。日常写界面用预览器，调系统能力用模拟器或真机。

预览器是三者的"效率之王"：它不启动完整系统，只渲染你当前页面的 UI，改一行代码。零点几秒就能看到效果。它的局限是"只渲染 UI"，涉及系统能力（网络请求、传感器、分布式）时预览器给不了真实环境。日常开发的节奏是：预览器里快速迭代界面（一秒钟看一次效果），界面定型后上模拟器或真机验证功能。

模拟器的首次设置比预览器麻烦一点：要在 Device Manager 里创建模拟器实例（选机型和系统镜像，镜像首次会自动下载）。模拟器的优势是"完整系统"，你可以模拟登录、分布式流转、通知等真机行为，还能模拟多设备协同（鸿蒙的看家能力）。缺点是吃资源：8GB 内存以下的电脑跑模拟器会卡，建议内存 16GB 以上再开。

真机调试的步骤：手机开启"开发者模式"（设置 → 关于手机 → 连点版本号七次）和"USB 调试"，数据线连电脑，DevEco 会识别设备并提示授权。真机的价值是"最终真相"，预览器和模拟器都通过的功能，上真机再验一遍才算数（不同机型的屏幕、性能、系统版本差异，只有真机能暴露）。第 74 章讲 UIAbility 生命周期时，真机观察更是不可替代。

这段代码你只需要"感受"三件事：@Entry/@Component 是装饰器；build() 里写界面（声明式，和 Compose/SwiftUI 一个思路）；@State 标记的状态变量一变，界面自动刷新。<strong>细节看不懂完全没关系，第 72、73 章会掰开揉碎讲。</strong>

不过有一个共同点值得现在就指出：这段代码里的 Column、Text、Button 都是"组件"：你声明"要什么"，框架负责"怎么画"。这和第 51 章的 Jetpack Compose（@Composable 函数）、第 62 章的 SwiftUI（View 结构体）是同一个范式。声明式 UI 已经是三大平台的统一答案，学过任何一家，另外两家都是"换语法不换思路"。这也是为什么本书把三大平台并排讲，你不是在学三套系统，是在学一套思路的三种表达。

#### 四、升级与对齐：IDE 新了，SDK 不能旧

鸿蒙环境最容易踩的坑是「IDE 装了新的，SDK 还是旧的」。这条对齐规则值得贴在显示器上：

- <strong>命令行工具同步升级</strong>：CI 或脚本构建用的命令行工具，要升到与 DevEco Studio 相同的版本，否则"本地能编译、流水线里挂"。
- <strong>升级后跑一遍 API 变更助手</strong>：菜单 Tools → API Change Assistant 能列出工程里行为发生变化或已废弃的 ArkTS / C API，还带适配指引链接。
- <strong>新旧设备都要测</strong>：官方升级流程明确要求在新旧两代设备上都做兼容性验证，通过了再发布到 AppGallery。

API Change Assistant 值得多说两句：它是鸿蒙生态"负责任地淘汰旧 API"的工具化体现。鸿蒙的 API 迭代很快（第 70 章讲过一年一大版），每次升级都可能有接口被标记废弃或行为变更，人工对照变更日志容易漏，这个工具直接扫描你的工程代码，列出"哪些调用会受影响"并给出适配建议。第 76 章的实战项目升级时会再用到它。

新旧设备都要测这条，对个人开发者容易犯的错是"只有一台测试机"。鸿蒙设备碎片化虽然远轻于安卓（华为自家设备为主），但不同机型的系统版本差异依然存在。穷人的解法：模拟器创建两个不同 API 版本的实例（新版 + 老版），代替真机覆盖。有条件的话，找家人朋友的旧华为手机借来测半天，比任何模拟器都真实。

#### 五、常见报错排查手册：十个最常撞见的错

环境搭建的重头戏不是安装，是报错。这一节把新手最常见的十个错按"症状 → 根因 → 解法"整理好，建议收藏：装环境那天你大概率会撞上其中一两个，撞上时回来对号入座，比漫无目的地搜省半小时。先记一个心法：报错信息里的英文原文别翻译成中文再搜，直接复制原文去搜，命中率高得多，报错的最后一行往往信息量最大，从那里开始看。

##### 报错一：构建或预览时报 Node/npm 相关错误

症状：项目建得好好的，一点构建或一开预览器，输出窗口刷出一长串 npm、hvigor 相关的红色报错，类似"Unsupported engine"或某个模块找不到。这就是本章第一节那个 Node.js 坑的典型发作。

根因：本机全局 Node 版本和 DevEco 工具链要的版本对不上。前端开发者的电脑尤其高发，全局 Node 往往比工具链需要的新得多，一些构建脚本依赖的东西在新版里已经被移除了。

解法：进 [Settings] → [Build]，把 Node 路径切到 DevEco 内置推荐版本，然后重启 IDE 让环境变量生效。只改不重启，报错会原样再来一遍，很多人在这一步误以为"改了没用"。你是前端老手、坚持用 nvm 管全局版本的话，就给鸿蒙项目单独切一个版本，接受"偶尔要切来切去"的代价。

##### 报错二：路径里的中文与空格

症状：项目能创建，一编译就报各种"文件找不到"，报错里的路径要么乱码要么断在半截。

根因：Windows 下，SDK 安装路径、项目路径或缓存路径里带中文、空格或特殊字符，构建工具解析路径时翻车。这属于"装的时候图省事，装完之后天天还债"的经典坑。

解法：SDK、DevEco 本体、项目目录，三样都放纯英文路径，别带空格。检查入口是 [File] → [Project Structure] → [SDK Location]，顺便把"SDK 到底在哪"这个疑问一起解决。已经踩了的话，最省事的修法是重装到英文路径，手工改环境变量也能修，但花的功夫比重装还多。

##### 报错三：模拟器启动失败

症状：Device Manager 里点了启动，进度条走一半消失，或者模拟器窗口闪退、黑屏。

根因通常三选一：CPU 虚拟化没开；内存被其它程序占光了；镜像文件下载损坏。Windows 家庭版用户还可能碰到系统版本支持问题。

解法按顺序排查：先开任务管理器 → 性能 → CPU，看"虚拟化"那行是不是"已启用"，没启用就重启进 BIOS 打开（不同主板的入口不一样，搜"主板型号 + 开启虚拟化"）；第二步，关掉占内存的大程序再试；第三步，把模拟器镜像删了重新下载。三步走完还失败，把报错原文拿去搜，别在同一个地方硬试一小时。

##### 报错四：设备列表是空的

症状：真机插好了，Run 按钮旁边的设备下拉框空空如也；命令行执行 <code class="inline">hdc list targets</code> 返回 [Empty]。

根因按概率排序：手机上的 USB 调试没开；那道"允许 USB 调试吗"的授权弹窗没点允许；数据线是只能充电的线；Windows 缺驱动。第四条在老台式机上偶尔出现，前面三条占了绝大多数。

解法：先在手机上确认开发者模式和 USB 调试都开着，然后拔插一次数据线，眼睛盯着手机屏幕：授权弹窗出现几秒不点就自己消失，很多人是错过了它。还不行就换一根确定能传数据的线，再不行就在命令行里重启 hdc 服务（先停再启，参数用 <code class="inline">hdc -h</code> 查），重启完再 list 一次。

##### 报错五：签名与安装失败

症状：构建成功了，往真机装的时候报 Install Failed；或者构建阶段直接报签名相关的错误。

根因最常见三个：没登录开发者账号（自动签名要账号）；改过 bundle name 但签名配置没重新生成；调试证书或描述文件过期了。

解法：[File] → [Project Structure] → [Signing Configs]，勾上自动签名并确认账号已登录；改过包名的，把签名配置取消再重新勾一遍，让它按新包名重新生成。调试签名的文件是有有效期的，隔了一阵子没打开项目，再遇到签名报错，先想到"可能是过期了"，重新生成一次就好。签名的完整逻辑下一节展开。

##### 报错六：应用装不上去（版本对不上）

症状：模拟器或真机上以前装过这个应用，改了配置之后再装，报安装失败。

根因多半是新旧版本冲突，或者你的 compatibleSdkVersion 写得比设备系统版本还高，设备装不了"声明自己比它新"的应用。

解法：先在设备上卸载旧版再装；装不上再回头检查 build-profile.json5 里 compatibleSdkVersion 和设备系统的版本关系。顺序别反，很多人一上来就改配置文件，改了半天发现就是把旧应用卸了就能解决的事。

##### 报错七：预览器白屏或一直转圈

症状：Previewer 窗口打开了，但一片空白，或者右下角进度条转个不停。

根因八成还是 Node 或者缓存：预览器底层依赖 Node 运行时，Node 版本不对它就摆烂；缓存脏了也会白屏。

解法：先按报错一把 Node 切到内置版本，重启 IDE；还不行就 [File] → [Invalidate Caches] 清缓存重启。预览器白屏看起来吓人，但它不牵扯任何真机硬件，排查面很窄，一般两步之内能解决。

##### 报错八：同步卡住、构建极慢

症状：进度条卡在 Sync 很久不动，或者每次构建都要等很久，同事的电脑秒过。

根因多半在网络：依赖和组件要联网下载，公司防火墙、不稳定的代理、校园网的限制都可能把它拦住。

解法：换个网络试试（手机热点是最快的验证方法）；如果在公司内网，找 IT 确认有没有拦截；需要配置镜像或代理的，按官方文档的指引来，别挂一个来路不明的加速器，省的那点下载时间，不够你排查它引入的怪问题。

##### 报错九：构建进程内存不足崩溃

症状：构建到一半，后台构建进程崩了，报错里带内存相关的字样。

根因：构建工具本身吃内存，浏览器开着几十个标签、其它 IDE 同时开着，内存就见底了。

解法：构建前把不用的程序关一关；在 DevEco 的设置里调大构建内存上限（有这个选项，位置以你版本里的设置项为准）；长期来看，内存是开发机最值得加的硬件，比换 CPU 管用。

##### 报错十：端口被占用

症状：模拟器起不来，或者日志、调试窗口连不上，报错里带 port in use 或端口占用字样。

根因：其它软件占了 DevEco 要用的端口，常见嫌疑犯是代理工具、游戏加速器，以及上一次没退干净的残留进程。

解法：先重启电脑，最笨但命中率最高；还不行就在任务管理器里找可疑的残留进程结束掉；频繁冲突的话，去 DevEco 设置里找相关端口的配置项改一个（有配置项，具体位置视版本而定）。玩加速器的同学记住：开模拟器前先把加速器关了，能少踩一半的端口坑。

##### 报错十一：安全软件"帮倒忙"

症状：构建莫名其妙失败，重装也不见好；或者安全软件的隔离区里躺着 DevEco、模拟器相关的文件，而你压根没主动删过任何东西。

根因：构建工具、模拟器内核这类"行为像虚拟机和编译器"的程序，是安全软件误判的重灾区。它不认得你在干什么，只看到"一个程序在大量读写文件、还想调用虚拟化能力"，于是出手。误删一个组件文件。构建就瘸一条腿，而且报错信息完全不会告诉你"文件是被杀软删的"。

解法：把 DevEco 安装目录、SDK 目录、项目目录加进安全软件的信任区或白名单（具体设置项以你装的安全软件为准）；被隔离的文件先还原，再加白名单，然后跑一次构建验证。这条在排查顺序里排位不高，但当你发现"报错原文搜不到同款"时，回头翻一眼隔离区，常有惊喜。

##### 报错十二：系统时间不对，下载组件报证书错误

症状：下载 SDK 组件或依赖时，报安全连接、证书相关的错。换网络、换手机热点、挂代理全试过，照样失败。

根因：电脑系统时间偏差太大。安全证书按时间校验有效性，时间不对，一切加密连接都可能被判定可疑，服务器没错，你的时钟在捣乱。这个错在"换什么网络都没用"的下载报错里命中率不低。

解法：系统设置里打开"自动设置时间"（时区也要选对，差一个时区都可能出问题），校准后重启 DevEco 再试。整个过程十秒钟，所以它值得你在放弃之前最先试一次。

##### 复盘：一次不看群、不问人的完整排查

把几个高频报错串成一个小故事。上周五晚上十点，读者小陈第一次装环境：创建项目正常，一开预览器白屏，对上报错七，把 Node 切到内置版本，重启 IDE，解决，用时五分钟。接着连真机，设备列表空的，对上报错四，拔插数据线、盯着手机把授权弹窗点掉，解决。最后一步装应用报 Install Failed，对上报错五，想起自己下午手痒改过 bundle name，进 Signing Configs 把自动签名取消再重新勾上，十分钟后图标躺在手机桌面上。

整个过程没人帮忙，全靠对照手册：先看报错像哪一条，再按解法走，一条不行换下一条。注意他的节奏：每个报错的排查用时都在十分钟以内。反过来讲，如果你在某个报错上卡了半小时还没头绪，就别再逐条硬试了，说明它不在手册覆盖的范围内，直接切到第十一节的自救三步，把时间花在搜和问上。

还有一条隐性收获别浪费：每次排查成功，花一分钟把"报错原文 + 解法"记进你自己的笔记。手册再全也覆盖不了所有机器的个性，你的笔记会慢慢长成"专属于你那台电脑"的排查手册，这才是环境搭建留给你最值钱的东西。

#### 六、模拟器进阶：多设备、分布式与端口的那些事

第一台模拟器你已经会建了。但模拟器真正的价值要开到第二台才显现：想象一个场景：晚上十点，你在准备第 76 章的实战项目，想验证"手机上点一下，内容接着在平板上继续"这个鸿蒙看家能力。只有一台模拟器，这事没法测；两台同时开着，它就发生了。这一节讲怎么把模拟器用出真机之外的价值。

##### 创建多台：一台新版，一台老版

入口还是 Device Manager → New Emulator：选机型、选系统镜像、起名字。建议给每台起带版本信息的名字，比如"phone-新API"和"phone-老API"，设备列表里一眼分清，不会装错。

两台模拟器的分工要提前想好。一台建最新 API 版本的镜像，日常开发、看最新能力；另一台建老一点的 API 版本，验证第四节说的"兼容性"：你的应用在老系统上跑成什么样，靠它先筛一遍，比借遍全家的旧手机省事。镜像下载几个 GB，建第二台之前先看一眼磁盘剩余空间，别把系统盘塞爆。

机型上也可以拉开差异：一台手机机型测竖屏主流程，一台平板机型测自适应布局，第 73 章讲多设备适配时，这套"手机 + 平板"的组合会天天用。

##### 分布式模拟：两台窗口就是两台设备

两台模拟器同时开起来，在你的电脑上就是两个独立的系统窗口。跑同一个应用的两台设备互相发现、互相流转，分布式能力可以先用模拟器建立直观感受，不必等真机凑齐。

代价要说清楚：每台模拟器都是一个完整系统，两台同时开对内存的要求翻倍。16GB 内存的机器开两台是舒服的，8GB 的机器开一台都紧张。后者直接跳过这招，攒点钱或者上真机。开两台的时候把浏览器标签收敛一下，这不是玩笑，是省内存的实际行动。

##### 分步实操：从一台到两台

把上面的思路落成清单，每一步都写上"你会看到什么"。第一次建第二台模拟器，跟着走：

1. 打开 Device Manager，点新建模拟器，弹出机型选择窗口。
2. 机型选平板（第一台是手机的话），列表里机型比你想的多，别纠结，选个主流平板就行。
3. 系统镜像选一个和第一台不同 API 版本的，每一项右侧有版本号，看清再选。
4. 给模拟器起名："tablet-老API"这种带版本的名字，名字是给三个月后的你看的。
5. 确认磁盘剩余空间，新镜像又是几个 GB 的量级，紧张的话先清理再继续。
6. 点完成，等下载和初始化，进度条会跑几分钟到十几分钟，取决于网速。
7. 启动它，第一次开机和新手机一样，会走系统初始化向导，按屏幕点完。
8. 两台都开着，开任务管理器看一眼内存占用，心里有个数，知道自己的机器能扛几台。

##### 场景案例：周日下午的平板适配预演

一个真实的使用节奏。你要在下周开始第 73 章的多设备适配，提前花半小时做预演：手机模拟器和平板模拟器同时开，同一个 Hello 项目分别装进去跑。手机上居中显示很正常；平板上同样的界面直接被拉宽，字大得像标题：这就是"没做适配"的原始长相。

预演的价值就在这半小时：你提前知道了坑长什么样，第 73 章学到断点、自适应布局时，你是带着"我见过那个丑样子"的问题来的，学起来完全不同。学习成本没变，但学习时机提前了：这招对任何"下一章才学"的内容都适用。

##### 给模拟器"减负"的日常习惯

模拟器的流畅度，一半靠机器配置，一半靠使用习惯。几条立竿见影的：用完就关，别让模拟器挂一下午后台；构建代码时不开模拟器，先把构建跑完，再启动模拟器验证，两个"大胃王"别挤在一张桌子上吃饭；内存吃紧的机器，在设置里找模拟器性能相关的分配项（具体位置视版本而定），调低一点，牺牲流畅换能跑。

还有一条前面埋过伏笔：同一台电脑上，安卓模拟器和鸿蒙模拟器别同时开。不只是端口打架，两者的虚拟化资源也是争抢关系，同时开的结果就是两边都卡成幻灯片，你以为鸿蒙模拟器难用，其实是内存被隔壁吃光了。

{class="mt-1"}
模拟器"灵异三连"的处置顺序：先冷启动（丢弃快照重来），再重启 hdc 服务，最后删镜像重建。八成的怪问题死在第一关。顺序别反，删镜像重建是杀伤力最大的一步，重来的下载时间和初始化向导，能省则省。

##### 快照与冷启动：快和稳的取舍

模拟器默认支持快照：关闭时把当前状态存下来，下次启动直接回到关机前的样子，秒开。日常开发要的就是这个快：上午关机，下午接着调，状态都在。

但快照用久了会出怪事：模拟器行为不对劲、连不上、卡在奇怪的状态，而你的代码明明没问题。这时候用"冷启动"——丢弃快照从头启动一次，相当于给模拟器重启系统。遇到"模拟器灵异事件"，第一反应就是冷启动，第二反应才是删镜像重建。

##### 端口冲突：加速器和残留进程是惯犯

第五节讲了端口占用的解法，这里补一个模拟器特有的场景：模拟器启动时要占用一组端口和设备资源，跟其它虚拟化软件、安卓模拟器、加速器是天然的争抢关系。同一台电脑上，安卓模拟器和鸿蒙模拟器尽量别同时开，资源打架、端口打架，两边都变慢。

判断是不是端口问题的办法很朴素：报错里带 port 字样就往端口冲突想；不带就先按"虚拟化 → 内存 → 镜像"的顺序走。改端口的配置项在 DevEco 设置里能找到（位置视版本而定），改之前记下原值，出问题好退回去。

{class="font-semibold"}

{class="mt-1"}
模拟器能测的是"系统行为"，不是"硬件行为"。传感器、通话、短信、真实摄像头、真实性能表现，这些模拟器给不了真值。上架前（第 78 章）的回归测试一定要在真机上做一遍，模拟器全绿不等于真机没问题。

#### 七、真机调试详解：证书、无线连接与 hilog

模拟器是排练厅，真机是正式舞台。第三节你已经连过一次真机，这一节把真机调试的三块硬知识补齐：签名证书到底是什么、无线调试怎么开、日志怎么看。这三件事贯穿后面所有章，第 74 章观察生命周期、第 76 章实战联调、第 78 章上架，全在这套流程里。

##### 签名与证书：它到底在验证什么

先建立直觉：签名就是给应用盖公章，系统靠这个章确认"这应用是谁的、有没有被篡改"。调试阶段装到手机上的应用，用的是"调试签名"；上架 AppGallery 的应用，用的是另一套更严格的发布签名（第 78 章细讲）。两个阶段、两套章，互不通用。

如果你来自安卓阵营，可以把调试签名理解成"系统帮你自动生成的 debug keystore"；来自 iOS 阵营的同学，它接近"开发证书 + 描述文件"的组合，但流程被大幅简化了。简化到什么程度？DevEco 里的自动签名：登录账号、在 [Signing Configs] 里勾上自动生成，IDE 就替你办完证书、描述文件的全部手续。学习阶段不用碰手动签名，它不是"更专业的做法"，是发布阶段才需要的事。

自动签名的产物有时效，过期了再装应用就会报签名错误——解法第五节讲过：取消勾选再重新勾上，让它重新生成。这个动作以后每隔一阵子就会做一次，别慌，不是环境坏了。

##### 无线调试：把那根线甩掉

场景：晚上十一点，你窝在被窝里调界面，手机在床头充电，数据线只有半米长，这时候无线调试就是刚需。开启方式的大致流程：手机和电脑连同一个 Wi-Fi，在手机的开发者选项里打开无线调试，然后在 DevEco 的设备连接入口里按提示配对（输入手机上显示的配对码），成功后设备列表里会出现这台手机，跟插线一样用。

具体入口和按钮名称随版本有差异，找不到就按第十一节的自救三步查官方文档，一分钟的事。无线比有线慢一点，装包、刷日志都有可感知的延迟，日常写 UI 用预览器没这烦恼，真机验证功能时这点延迟可以忍。

两个注意：无线调试走的是局域网，公共 Wi-Fi 上别开；调完记得把无线调试关掉，跟电脑断开 SSH 不关是同一个性质的习惯问题。

##### hilog：学会看日志，你就出师了一半

鸿蒙的日志系统叫 hilog。看它的地方是 DevEco 底部的 Log 窗口：应用一运行，日志哗哗地流，不是"看全部"，是"过滤"。三样过滤器最有用：按设备选、按进程选、按级别选（Debug/Info/Warn/Error）。先选对设备和进程，日志量立刻少一个数量级；再看级别，Error 开头的先处理。

命令行党也有工具：<code class="inline">hdc list targets</code> 确认设备在线，连上后可以在终端里直接刷设备日志（命令细节用 <code class="inline">hdc -h</code> 查，以官方文档为准）。IDE 的 Log 窗口覆盖九成场景，命令行在"IDE 卡死、设备连着、要看日志"这种时刻救场。

写日志的习惯现在就养成：给自己的日志打上统一前缀的 tag，比如项目名缩写加模块名，过滤框里一输 tag，属于你代码的日志整整齐齐跳出来。没有 tag 的日志，和没有信封的信一样，只能一封封拆。

##### 无线调试分步清单

把上面的流程落成一步步的清单，每步带上"你会看到什么"：

1. 手机和电脑连同一个 Wi-Fi，注意是"真同网"，手机开热点给电脑连这种不算稳。
2. 手机：设置 → 开发者选项 → 打开无线调试，开关旁边会出现"使用配对码配对设备"的入口。
3. 电脑：在 DevEco 里找到设备连接入口（不同版本位置略有差异，设置里搜"无线"一般一步直达）。
4. 发起配对，手机弹出配对码，一串数字，停留时间不长，看着手机别走神。
5. 在电脑端输入配对码确认，设备列表里出现这台手机的型号，和插线时长得一模一样。
6. 点 Run，应用装进手机，这根线从此和你无关。
7. 收工后到手机上把无线调试关掉：习惯问题，前面说过，不重复。

第一次配对失败别慌。两个高频原因：配对码超时（重新生成一个再试）；不同网（公司访客 Wi-Fi 常把设备互访隔离，换用自己的热点反而顺利）。重试的成本是分钟级，不值得为它翻文档超过十分钟。

##### 场景案例：凌晨十二点半，八分钟定位一次闪退

感受一下 hilog 在实战里的样子。场景：一个详情页，模拟器上好好的，真机上一点就闪退，百试百灵。打开 DevEco 的 Log 窗口，三步设置：选对设备、选对进程、级别过滤到 Error。然后开着过滤复现一次闪退，屏幕上跳出的最后几行日志里，有一行明确指向"空值引用"。

回到代码，定位到那个页面取数据的地方：接口偶尔返回空，界面代码没兜底，真机网络稍慢就撞上了。加一个空值判断，重新运行，闪退消失。全程八分钟，靠的不是聪明，是过滤器用得对，没有过滤，你要在一千行滚动日志里肉眼找一行，八小时都不一定够。

这个案例里藏着一个通用规律：日志要看的是"最后一屏"，不是"从头刷屏"。崩溃信息的末尾才是结论，前面的一大段大多是过程铺垫。先用过滤器把范围砍到只剩 Error，再读末尾。这是新手和熟手看日志的最大差别。

##### 连上真机先做的三件体检

#### 八、DevEco 的 AI 辅助：补全、问答与报错问诊

第 41 章讲过，AI 编程工具已经分了工种：浏览器里的对话助手管"讲解和方案"，编辑器插件管"边写边补"。DevEco 把后一种直接装进了 IDE，新版本内置了 AI 辅助能力，包括更懂鸿蒙的代码补全和可以对话的 AI 面板。本节先说清楚一件事：这些功能随版本演进，你的 DevEco 里找不到某个入口，说明版本较早或该功能有地区/账号要求，一切以官方文档为准，别对着截图硬找。

##### 内置补全：懂鸿蒙的"接话搭档"

你在第 72 章写 ArkTS 时会体会到差别：通用插件的补全像"什么都会一点的同事"，知道任何语言的一般写法；DevEco 内置的补全更像"组里写鸿蒙的老手"，在 Column 里打字，它建议的是布局组件；写事件回调，它建议的是鸿蒙的事件 API。因为模型见过大量真实鸿蒙工程，它给出的补全往往贴合 ArkUI 的惯用结构，改起来省力。

第 37-47 章学的提示词技巧在这里同样适用：写清楚意图，补全质量就高一截。注释里先写"这一段做什么"，AI 补全会往你描述的方向靠，你写得越像需求文档，它接得越准。

##### AI 问诊：把报错交给它解释

新版 DevEco 里有 AI 对话入口：选中一段报错，问它"这是什么意思、怎么修"；或者贴一段代码，问它"这段为什么编译不过"。它相当于随叫随到的鸿蒙同事，尤其适合第五节那十个报错以外的"野生报错"，官方文档覆盖不到的长尾问题，先问 AI 再搜社区，顺序反了会浪费时间。

问诊的提问方式决定答案质量。差的问题："报错了怎么办"；好的问题："构建报错如下（贴原文），我的 SDK 版本是 X、设备系统是 Y，昨天还能编译，今天改了 Z 之后开始报，帮我定位原因"。上下文给得越足，它越少瞎猜。这套提问框架第 41 章讲过，环境搭建是它最划算的应用场景。

##### 错误示范：整段粘贴的代价

错误示范：小李让 AI 生成了一个"带下拉刷新的列表页"，八十几行代码整段粘进项目，能跑，他很高兴。两周后产品要改交互，他盯着代码发现每一行都认得、连起来不知道为什么这样写，最后宁可让 AI 重新生成一遍，也不敢手动改。这就是"AI 债"：省下的学习时间，后面连本带利还回去。

正确姿势三条：粘之前让 AI 逐段解释"这段用了哪些 API"；粘之后用 Tools → API Change Assistant 扫一遍，AI 训练数据可能滞后，它给的可能包含废弃写法；自己至少改动一处小地方（换个文案、调个颜色）并让预览器刷新验证：改得动，才算你的代码。

分工建议收个尾：环境报错解释、语法学习时的"这是什么"，用内置 AI，它离你的工程上下文近；跨项目的大方案设计，用你顺手的通用工具（第 41 章那套）。工具没有高低，就近使用效率最高。

#### 九、项目结构与工程配置进阶：多模块、资源限定词与构建模式

第二节你认识过 entry 模块和那几张配置文件，那是"能跑起来"的最小集。这一节往深一层：工程长大以后怎么拆、资源和多语言怎么组织。debug 和 release 怎么切。现在先混个脸熟，等第 76 章实战项目结构复杂起来，你会回来翻这一节。

##### 多模块：工程什么时候该拆

鸿蒙的模块不止 entry 一种：入口模块（entry）之外，还有按需加载的功能模块（feature，类似安卓的 Dynamic Feature）。以及两种"被打包引用"的共享形态，静态共享包和动态共享包（官方叫 HAR 和 HSP，细节以官方文档为准，本书实战只用得到 HAR 这种最简单的）。它们的分工一句话说清：entry 管入口，feature 管独立功能，HAR 管被多个模块复用的公共代码。

什么时候该拆？给一个不纠结的答案：学习阶段不拆，一个 entry 跑通所有章节；当你发现某个功能的代码被两处引用、或者团队开始分工（每人负责一个 feature），才动手拆。过早拆模块是新手工程病的常见症状，模块边界没想清楚，拆出来的是四个互相纠缠的碎块，比不拆更乱。右键工程 → New → Module 可以新建，模板里有各类型的说明，建之前先把官方那页文档读完。

##### 资源限定词：一份代码，多种长相

第二节提过 resources/base 放默认资源。真正的结构是：base 之外可以按"限定词"建平行目录，设备匹配到哪个目录就用哪个，base 永远兜底。常用的三类限定词：语言地区（如 zh_CN、en_US，管多语言）、深浅色（dark，管深色模式）、设备形态与分辨率类（管平板、折叠屏的差异化资源）。

用一个最实用的例子感受它：深色模式。你在 resources 下建一个 dark 目录，放一套深色用的颜色资源，名字和 base 里的浅色资源一模一样，系统切到深色模式时自动用 dark 目录的值，切回浅色自动换回来，你的代码一行都不用改。多语言同理：string.json 在 zh_CN 目录放中文、en_US 目录放英文，设备语言决定用哪套。这就是第二节说"字符串全部资源化"的真正回报，不做资源化，这些自动化就与你无关。

新手常问：限定词目录名写错了怎么办？写错了它就不生效，应用默默回落到 base，不会报错，只是"没变化"。所以做完深色资源后，手动切一次系统深色模式验证，别以为目录建了就完了。

##### 构建模式与产物：debug 和 release 不是一回事

IDE 里那个构建按钮旁边，藏着两个模式：debug（调试版，带调试能力，跑起来慢，只用来开发时装）和 release（发布版，速度调过、要正式签名，是上架 AppGallery 的那一版）。日常开发一直在 debug；到第 78 章上架时才第一次打 release：到时候你会遇到 release 独有的检查项（比如混淆和正式签名），那是另一天的功课。

再进一层：build-profile.json5 里还能定义多个"产品形态"（products），比如同一份代码打一个免费版和一个会员版，图标名不同、配置不同。这个功能现阶段你只需要知道存在，第 76 章实战会用一个最简单的双产品配置演示它。

#### 十、给三类背景读者的路径建议：各有各的坑

章首的三类读者画像，现在兑现成三条具体路径。每条路径两件事：哪些旧经验能直接搬、哪些旧习惯必须丢。第一周照着走，第二周你就不需要这一节了。

##### 前端转来的：语言最亲，边界最陌生

能直接搬的：ArkTS 基于 TypeScript，语法不用学，重点是把第 72 章列的"ArkTS 收紧了哪些东西"读两遍；声明式 UI 和 React 是一套思路。组件、状态、单向数据流的概念全部平移；预览器的秒级刷新，体感约等于 Vite 的热更新，开发节奏接得上。

必须丢的习惯有三个。第一个，别找 DOM，没有 document，没有 window，你以为的"浏览器环境"不存在；等价物是 ArkUI 的组件树和系统能力接口。第二个，别把样式当 CSS 写：ArkUI 的属性挂在组件上（fontSize、width），不是写在样式表里，长度单位也不是 px，动手前把官方"单位与像素"那页翻一遍。第三个，别随手 any：前端项目里 any 满天飞能跑，ArkTS 直接编译不过；类型报错别烦，它在帮你，卡住了用内置 AI 问诊解释报错，比硬啃文档快。

第一周任务：跑通本章 Hello 项目 → 把第二节的目录对照表抄一遍 → 用 ArkTS 重写一个你做过的最简单 React 组件（一个计数器就够）。做完这三件，你已经"在鸿蒙里用前端的肌肉记忆写代码"了。

##### 安卓转来：概念最亲，映射要重学

能直接搬的：整套工程世界观：Manifest、构建系统、权限声明、生命周期、日志系统，概念一一对应，只是名字换了：module.json5 对应 AndroidManifest，hvigor 对应 Gradle，hilog 对应 logcat，UIAbility 对应 Activity。环境搭建这一章对你只是"换个 IDE"，两小时的事。

必须丢的习惯也有三个。第一个，别硬找"一模一样的 API"，正确顺序是先查"这个概念在鸿蒙叫什么"，再看官方推荐写法；硬把安卓写法翻译过来，编译器会用一百个红波浪线提醒你这条路不通。第二个，别把生命周期的经验当全对，Stage 模型的生命周期和安卓不是一一对应，第 74 章会掰开讲，在那之前别凭直觉写。第三个，别急着折腾手动签名：安卓的 keystore 习惯会驱使你去"好好管一下证书"，而鸿蒙调试阶段自动签名包办一切，你只需要在它过期时重新生成。

第一周任务：跑通 Hello 项目 → 用 hilog 打三条不同级别的日志并在 Log 窗口过滤出来 → 把 entry 的生命周期日志都打出来，观察冷启动到回到前台的完整序列。做完这三件，第 74 章你会读得飞快。

##### iOS 转来：范式最亲，门槛反而最低

能直接搬的：SwiftUI 和 ArkUI 几乎同构，struct、属性包装、声明式 body，你写起来会有"这不是我们家 SwiftUI 吗"的错觉；签名体系"证书 + 描述文件"的概念完全对得上，只是自动化程度更高；预览器对应 SwiftUI 的 Canvas 预览，连交互方式都像。

必须丢的三个习惯。第一个，别以为需要 Mac，这是 iOS 开发者对鸿蒙最普遍的误解，Windows 全程可用，模拟器也不需要额外的加速配置；你甚至可以在公司 Windows 电脑和家里 Mac 之间自由切换。第二个，别急着手动管证书，iOS 证书管理的痛痕会让你下意识想"提前搞清楚签名体系"，忍住，调试阶段自动签名就是正确答案，第 78 章才需要你动手。第三个，别找 Interface Builder，没有 Storyboard，没有 XIB，UI 全在代码里声明，这对你反而是好消息，少一个学习对象。

第一周任务：跑通 Hello 项目 → 把 Hello 项目的 Index.ets 逐行对照你写过的某个 SwiftUI View，写一份映射笔记 → 在模拟器里跑一次，体验"不用 Mac 也能跑模拟器"这件事。做完这三件，你对"跨平台思维是同一套"这句话会有切身体感。

三类读者最后交一条共同任务：第一周别比较优劣。你现在积累的所有不爽。都是"不熟悉"而不是"不好"；先用满一周，再下判断——这个心态在本书第 37-47 章学 AI 编程时同样管用。

#### 十一、环境问题的"自救三步"：搜、查、问

设定一个场景：凌晨一点，你赶在睡前想把环境装完，报错停在半路，群里没人在线，教程评论区三天没人回复。这时候你需要一套不依赖任何人的流程，自救三步：搜、查、问。它不保证每次都解决，但保证你 30 分钟内穷尽自己能做的部分，而不是对着屏幕干耗两小时。

##### 第一步：搜，但会搜

错误示范：把"我装不上鸿蒙开发软件怎么办"整句丢进搜索框。这句话没有任何信息量，"装不上"可以是十种报错里的任何一种，搜索引擎只能给你十篇教程让你自己碰运气。

正确姿势：复制报错信息的原文去搜，优先最后一行，那行通常是结论性的。报错有编号或代码的，连编号一起搜；报错是英文的，直接用英文搜，再补一个 HarmonyOS 或 DevEco 关键词；中文报错就中文搜。同一问题搜中英文各一遍，前者的答案多来自社区帖子，后者多来自官方 issue，两边的信息经常互补。

还有一个搜的技巧：把你的版本号加进关键词。同一个报错，在不同版本的 DevEco 里成因可能完全不同，"报错原文 + 版本"的组合能把过时的答案筛掉一大半。

##### 第二步：查官方文档与发布说明

搜出来一堆二手答案，不代表它们是对的。鸿蒙迭代快，网上的教程从发布到失效，周期可能只有几个月，而官方文档永远跟着最新版本走。所以第二步是拿第一步搜到的关键词进官方文档验证：这个报错官方有没有给标准解法？开发者网站的 FAQ、发布说明（Release Notes）和变更日志是三个值得收藏的入口：尤其是升级环境后突然报错的情况，八成能在变更日志里找到"这个行为改了"的一行字。

这一步还有个隐藏收益：确认"不是我的问题"。有些报错是当前版本已知的 bug，官方在下一个版本里已经修了：知道这一点，你就不用再怀疑自己的操作，等一个更新或者换个版本绕过去，心态完全不一样。

##### 第三步：问，像工程师一样问

前两步穷尽了还解决不了，去官方开发者社区和开发者论坛发帖。发帖的质量决定回复的速度。一个让热心人"看一眼就能答"的提问模板，四行搞定：

- <strong>环境</strong>：操作系统、DevEco 版本号、目标设备（真机型号或模拟器镜像版本）。
- <strong>完整报错</strong>：复制粘贴原文，别截图、别只贴最后一行。
- <strong>复现步骤</strong>：做了什么操作之后报的错，从哪一步开始和教程不一致。
- <strong>已尝试</strong>：你搜到了什么、试了哪些方法、结果分别是什么。

这四行的作用不是礼貌，是省掉三轮来回追问。"已尝试"尤其重要，它让回答者不用再让你重走一遍弯路，也证明你不是伸手党。同样的模板在第十一节之外也通用：第 78 章上架遇到审核问题、第 76 章实战遇到框架问题，都这么问。

时间线再收一下：自己硬试的上限是 30 分钟；超了就走三步；三步走完还没解决，把电脑合上睡觉。一半的"诡异问题"睡一觉再看就眼熟了，大脑后台一直在跑这个线程，这不是玄学，是你第二天换了注意力带宽。

##### 实战演练：跟着三步走一遍

拿一个典型的虚拟案例把三步串起来。周一早上你升级了 DevEco，昨天还好好的项目，今天一打开同步就报错，报错末行带着依赖解析相关的字样。先别点"重试"，点一百次也不会有奇迹。

第一步搜：复制报错原文，加上版本号去搜。搜到几篇帖子，都说"删缓存重试"，照做，没用。注意这里的信息价值：删缓存没用，说明问题大概率不在缓存，这条弯路帮你收窄了范围，不是白走。

第二步查：拿着报错关键词进官方发布说明和变更日志，发现这个版本的构建行为确实有调整，升级指南里写了对应的迁移办法。照着改完，同步通过：问题解决了，全程没求助任何人。这个案例最值钱的瞬间是第二步：你把问题从"我做错了什么"翻转成"官方改了什么"，从自我怀疑变成按图索骥，路径和心态完全不同。

假如第二步没找到对应说明呢？那就进第三步，按四要素模板发帖：环境、完整报错、复现步骤、已尝试（记得把"删缓存无效"写上，这一行能帮回答的人跳过最俗的建议）。发完帖该干嘛干嘛，帖子不是你盯着屏幕等来的。

##### 三个反直觉的提醒

第一，"搜不到"不等于"没人遇到过"。多数时候是你截取的关键词不对，报错中间那些变量路径、随机哈希别带进去，只取句式的骨架；或者从最后一行换成倒数第二行再搜一次。换个关键词重搜，比换个搜索引擎有用。

第二，别跳过第二步直接问人。官方文档五分钟能确认的事，发帖可能要等几个小时，而且等你等来回复，很可能就是一句"文档里写了"。急着求助省下的五分钟，会用等待的时间成倍还回去。

第三，问题解决后花一分钟回写笔记：报错原文、根因、解法，三行。下一次同样的报错，你从"走三步"升级成"直接翻答案"。你的环境笔记就是这么一轮一轮长厚的，到第 76 章实战时，它会是你案头最常用的文件。

#### 十二、常见问题 FAQ

收集本章评论区出现频率最高的十个问题。提问都保留原味的情绪和错误前提，因为每个错误前提本身就是一个知识点。

<strong>问：我电脑 8G 内存，是不是没法学了？要不要先攒钱换机？</strong>

答：能学，但策略要变：日常用预览器（吃资源极少），模拟器少开、用完就关，最好借一台真机顶替模拟器的位置。别一边开着几十个浏览器标签一边开模拟器，内存就这样被吃掉的。换机可以等学到第 76 章实战再决定，到时候你对配置需求的理解会准得多。

<strong>问：一定要买华为手机吗？没有真机这章是不是白学了？</strong>

答：不用买，本章也没白学。预览器加模拟器足够覆盖本章全部内容，以及第 72、73 章的学习。真机的刚需出现在上架前（第 78 章的回归测试）和涉及硬件能力的功能（第 75 章起），到那时借一台也行，买入门款也行，别为"学个环境"先掏钱。

<strong>问：我是 Mac 用户，教程全是 Windows 截图，能跟吗？</strong>

答：能跟。安装、创建项目、预览器、真机调试的流程两个平台几乎一致，只有设置菜单位置和快捷键不同。模拟器在某些 Mac 上的表现视芯片与版本而定，遇到差异按第十一节的三步法查官方文档。

<strong>问：我电脑装过 Node.js 还跑着别的项目，会不会打架？</strong>

答：会，这正是本章第一节的老朋友。让 DevEco 用内置推荐版本，它的工具链自成一体，不碰你的全局 Node；坚持用 nvm 的话记得给鸿蒙项目单独切版本。两者并存没问题，"并存但互不干扰"就是设计目标。

<strong>问：C 盘实在满了，把 DevEco 装到移动硬盘行不行？</strong>

答：不推荐。移动硬盘速度慢会拖垮构建，换电脑插上盘符变了还会引出一堆路径报错。更稳的方案是把 SDK 和缓存挪到内置的其他盘，IDE 留在系统盘，空间大头是 SDK 和缓存，不是 IDE 本体。

<strong>问：预览器明明更快，为什么不干脆都用预览器，还要模拟器？</strong>

答：因为预览器只渲染 UI，不含完整系统：网络请求、通知、分布式这些能力它一概演不了。它俩是分工不是替代：写界面用预览器。测能力用模拟器和真机。砍掉模拟器，你的应用上线那天会第一次见到"真实系统"，风险全堆到那时候。

<strong>问：升级完 DevEco，老项目一堆红，打不开了，怎么办？</strong>

答：先别动配置。跑一遍 Tools → API Change Assistant，让它列出哪些 API 变了；再对照官方升级指南改。第四节那张升级步骤表就是为这个时刻准备的，按顺序走，别凭感觉大面积重写。

<strong>问：我只是想学着玩，实名认证和开发者账号能先跳过吗？</strong>

答：账号可以晚一点，但别晚过真机调试，自动签名要登录账号，不登录连不上真机。实名认证几分钟，免费，而且你第 78 章上架用的就是现在这个账号，早注册早一致。学习阶段个人账号完全够用。

<strong>问：学完这章，我写的应用是不是只能在华为手机上跑？值不值得投入？</strong>

答：先纠正一个隐含前提，"环境搭建学到跑通"和"生态值不值得投入"是两个问题，后者请去重读第 70 章的生态分析，那不是本章的任务。本章的承诺只有一句：花一到两个小时，你获得一个能跑第一个应用的环境和一套排查问题的方法。值不值这两个小时，跑完你自己判断。

<strong>问：装最新版还是装教程对应的旧版？网上教程版本都不一样。</strong>

答：装当前最新稳定版，别追内测版。旧教程和最新版的差异，用本章第五节的排查手册加第十一节的三步法消化，这本教材自身的更新也会跟着官方走。装旧版"为了跟教程一致"是反方向：你会错过修复，还把过时问题引进来。

<strong>问：模拟器里能装微信这类日常应用吗？装好了能不能当备用机用？</strong>

答：能装一部分，但别当备用机，方向就错了。模拟器是开发工具，不是虚拟手机：它没有电话、短信、真实摄像头这些硬件底座，日常应用缺了这些要么装不上要么功能残缺；而且它吃的是你电脑的内存和磁盘，挂一整天比你的真手机费电多了。拿它测试自己应用在"装了其它应用"环境下的表现倒是正经用途，第 76 章联调时会用到这一招。

<strong>问：报错全是英文，我英语不行，是不是学不了编程？</strong>

答：先把心放回肚子里，开发报错的英语词汇量极小，翻来覆去就是 not found、failed、cannot、invalid、unsupported 这几十个词，比背英语四级单词少一个数量级。而且你不需要"读懂全文"，只需要认出关键词，再交给第十一节的三步法：原文复制、搜索、让 AI 或文档给你翻译。用满两周你会发现。你熟悉的报错就这么几类，看到 Unsupported engine 直接联想到 Node 版本，那时你已经不需要翻译了。英语水平不构成门槛，构成门槛的是不肯复制原文去搜。

<strong>问：我的电脑配置比较特殊（老机器、ARM 架构轻薄本），装之前在哪确认支持不支持？</strong>

答：去官方下载页和系统要求说明里确认，那里有一份明确的操作系统与硬件要求清单，比任何教程（包括本书）都新、都准。下载页之外的判断渠道都不可靠，因为支持范围随版本在变。确认支持就装，不支持也不必沮丧：官方有时会提供云开发或远程方案（以官方文档为准），先用它们跟着学，攒到换机再补环境，本章知识一点不浪费。

<strong>问：这周实在没时间，环境装好了先放着，会不会"放坏"？下周回来还能用吗？</strong>

答：会"放坏"，但坏得很有规律，不用怕。放两周回来，最可能的三件事：调试签名过期了（重新生成，五分钟）；IDE 提示有更新（升不升都行，升了按第四节对齐）；磁盘被别的东西挤占或者你动过路径（体检清单能查出来）。所以正确姿势是：放着可以，回来先跑第十四节那八项体检，全绿再开工。环境不怕放，怕的是"放着不管 + 回来蛮干"的组合。

#### 十三、误区清单：这六条别信

最后一份收获清单，全是"很多人以为 X，其实 Y"的形态。它们不是错误操作，是错误观念，观念错了，操作会反复错出新花样。

- <strong>很多人以为装完 IDE 环境就搭好了</strong>，其实要三条路都验证过才算：预览器能刷、模拟器能开、真机能装。每条路各有一套依赖（Node、镜像、签名），缺哪条，哪条就会在你赶工的晚上找上门。
- <strong>很多人以为预览器里看到的就是最终效果</strong>，其实它只渲染界面，性能表现、系统能力、真机适配统统不含。预览器里的完美，只是"可以开始上模拟器了"的意思。
- <strong>很多人以为报错全是自己太菜</strong>，其实相当一部分是版本组合、已知 bug、网络环境的问题。先按第十一节搜一轮再评价自己，大部分时候，你只是碰上了环境的天气，不是自己不会走路的证明。
- <strong>很多人以为自动签名是偷懒不正规</strong>，其实调试阶段它就是官方推荐路径；手动签名是发布阶段的事（第 78 章），提前手动只会提前踩坑。
- <strong>很多人以为要先学透 ArkTS 才能开始动手</strong>，其实环境搭建和跑通项目不需要任何语言基础，本章第一节你什么都不懂也能跟着走。语言是边跑边学的，第 72 章会接住你。
- <strong>很多人以为默认安装路径无所谓</strong>，其实 C 盘空间和中文路径是两个经典雷区。装之前就想好放哪、都用纯英文，比装完之后挪十遍都省时间。

##### 再补两条：来自读者踩坑记录的教训

- <strong>很多人以为模拟器开得越多越专业</strong>，其实每一台都是一个完整系统，双开是测试分布式时的手段，不是日常状态。按需开、用完关，机器轻快、人也不烦躁——"工具常驻"和"工具在手边"是两种工作状态，选后者。
- <strong>很多人以为环境小毛病忍忍就过去了</strong>，其实路径的坑、Node 的坑这类"小病"会在后面章节反复发作，每次发作都要重新付一遍排查时间。当场修好，一次付清：这是本章所有节都在暗暗重复的同一句话。

环境这东西，搭好的那天感觉平平无奇，但它是后面十几章每一次"点一下 Run"的地基。而且它是个会成长的长期资产：你的体检清单、排查笔记、对照表，每过一章就厚一层，到第 76 章实战时，它们比任何教程都懂你的电脑。地基稳了，去第 72 章学 ArkTS，那里才是真正的第一课。

#### 十四、环境体检与迁移：换电脑、备份与多机办公

环境不是搭完就一劳永逸的。换电脑、重装系统、公司家里两台机器轮着用，这些场景迟早轮到你。这一节先给你一份"环境体检清单"（判断现在的环境健不健康），再讲怎么把环境搬到新机器上不翻车。

##### 环境体检：30 分钟确认一切正常

判断"我的环境到底健康吗"，别凭感觉，照着清单跑一遍。八个体检项，全绿就放心去写代码：

- <strong>IDE 启动无报错</strong>，[File] 菜单正常打开。
- <strong>SDK 同步完成</strong>：右下角进度条跑完，SDK Location 里路径正确且是纯英文。
- <strong>账号已登录</strong>：右上角头像在（真机调试和上架都靠它）。
- <strong>预览器能刷</strong>：Hello 项目改一行字，预览器跟着变。
- <strong>模拟器能开</strong>：至少一台启动并跑起 Hello 项目。
- <strong>真机能连</strong>：插线或无线，设备列表出现型号，Run 一次成功。
- <strong>日志能看</strong>：Log 窗口流出设备日志，过滤器工作正常。
- <strong>磁盘够用</strong>：SDK 和缓存所在盘剩余空间还有一截余量（别等到构建失败才发现满了）。

这份清单的使用场景不止"刚装完"：隔了两个月回来继续学、大版本升级之后、电脑中了奇怪的邪，跑一遍体检，哪里红补哪里，比"打开项目看看能不能跑"这种粗略验证靠谱得多。第 76 章实战开始前，也建议跑一遍。

##### 换电脑或重装系统：带走什么，留下什么

先说结论：要搬走的是"你的东西"（项目代码、你的笔记、你已经解决过的报错记录），要留下的是"环境的东西"（SDK、模拟器镜像、构建缓存），后者在新机器上重新装一遍，比搬运更稳。

为什么不直接拷环境？三个理由：SDK 和镜像里藏着与机器相关的配置，搬过去经常半身不遂；缓存（构建的中间产物）搬到新机器意义不大，还可能带着旧机器的脏状态；安装和同步的时间其实不长，网速正常的话一次重装也就一个下午，你在第五节练出来的排查能力，正好用来处理重装时的小报错。

迁移的正确姿势分四步：第一步，项目代码推到 Git 远端（第 44 章的技能，现在兑现）；第二步，翻出你的环境笔记，SDK 路径、Node 用内置还是全局、踩过哪些坑，照着笔记把新机器装成一样的；第三步，新机器跑一遍上面的八项体检；第四步，从 Git 拉代码，跑通 Hello 项目收工。整个过程最大的风险点是你凭记忆重装、漏掉某个自定义配置，所以笔记要趁记忆新鲜时写，不是搬家那天补。

##### 公司一台、家里一台：多机办公的正确姿势

两台机器开发同一个项目，纪律只有一条：<strong>代码的真相只有 Git 仓库里那一份</strong>。下班前 push，开工前 pull，谁也不许把改动留在本地过夜。用 Git 管起来之后，两台机器的差异只剩"环境各自装各自的"，这反而是好事，一台升级出了问题，另一台还是能干活的备份环境。

两台机器的版本要主动对齐吗？建议对齐：DevEco 版本差太多，会出现"公司能编译、家里打不开"（或反过来）的错位：就是第四节说的 IDE 与 SDK 对齐问题在两台机器之间的翻版。升级前在群里（如果团队用鸿蒙）或自己笔记里打个招呼，两台一起升。

签名在多机场景下有个小提醒：每台机器各自用自动签名，调试证书各归各的，互不影响：你不用、也不应该手动搬运签名文件。第一次在第二台机器上装应用报签名错，重新生成一次就好，这是正常现象不是故障。

{class="font-semibold"}
<i class="fas fa-exclamation-triangle mr-2"></i>避坑提醒

{class="mt-1"}
别把整个 DevEco 或 SDK 目录打包拷到新机器"图省事"。搬过去的环境大概率报一堆路径错误，排查它们的时间远超重装，而且你分不清哪个错是"搬坏的"，哪个是"新机器本来就有"的，问题叠加问题。环境用装的不用搬的，项目用拉的（Git）不用拷的（U 盘）。

#### 十五、动手清单：30 分钟把这一章跑扎实

读完不等于会了。这一节把全章内容压成五组动手练习，总耗时大约 30 分钟（网速影响下载类步骤）。每组都给了验收标准，做到了才算过，别用"感觉会了"骗自己。做完这五组，本章才算真正归你。

<strong>练习一：环境体检（约 5 分钟）</strong>

对照第十四节的八项清单跑一遍你的环境。验收标准：八项全绿；有红的，回到对应小节修到绿为止。这一步顺手把你的"环境笔记"开个头：SDK 路径、Node 策略、体检结果，三行就够，这个文件以后会越来越厚。

<strong>练习二：第二台模拟器（约 10 分钟，含下载）</strong>

按第六节的分步清单建一台不同 API 版本或不同机型的模拟器，两个 Hello 项目各跑一遍。验收标准：两台能同时开、各自流畅；你能说出每台模拟器的"名字 → 版本 → 分工"。8G 内存机器跑不动双开的话，验收标准放宽为"建成并单独跑通"，不硬撑。

<strong>练习三：无线调试连一次、断一次（约 5 分钟）</strong>

有真机的同学按第七节的分步清单走一遍无线配对，装上 Hello 项目，再按规矩把无线调试关掉。验收标准：全程不插线完成一次 Run；能说出配对失败时的两个高频原因。没有真机就跳过，用模拟器做练习四。

<strong>练习四：深色模式资源（约 5 分钟）</strong>

按第九节的讲法建一个 dark 限定词目录，放一套与 base 同名的深色颜色资源，界面代码用资源引用。验收标准：系统切深色，界面颜色跟着变；切回浅色，自动复原；全程没改一行界面代码。做不出来多半是"目录名拼错或资源名不一致"：它不报错，只是默默不生效，回头检查目录名。

<strong>练习五：日志过滤（约 5 分钟）</strong>

在 Hello 项目的按钮点击事件里加一条日志（具体 API 写法第 72 章展开，先照着官方文档照猫画虎，或者让内置 AI 给你写并解释），打上带项目前缀的 tag。验收标准：Log 窗口里用 tag 过滤。你的日志一眼跳出来；级别过滤器切到 Error 时它消失（如果你打的是 Info 级）。做这一步时你会提前摸到第 72 章的门槛，赚了。

##### 做完练习别急着关电脑：三问复盘

每组练习做完，花一分钟问自己三个问题，并写下答案，这是把"操作"变成"经验"的最后一道工序。一问：刚才哪一步和教程不一致？（不一致的地方就是你环境的个性，记进笔记。）二问：如果明天重来一遍，哪一步我会卡住？（那一步就是你下次的排查起点。）三问：这个练习和本章哪一节对应？（回链建立起来，以后忘了能一秒翻回原节。）

三个问题的答案加起来不过几行字，但它决定你两周后的复习效率：有复盘的人回来是"扫一眼笔记接上进度"，没有的人是"从头翻教程找状态"。学习时间的差距，就是在这一分钟一分钟的工序里拉开的。

五组全过的同学，你的环境已经不是"装好了"，是"被你驯服了"，知道它吃几碗干饭、闹脾气往哪儿查、搬家怎么迁。带着这份底气进第 72 章：语言会忘，环境的手感不会。中间遇到任何问题，第五节的手册和第十一节的三步法永远在原地等你。

#### 十六、三平台环境搭建对照速查：和第 50、60 章摆在一起看

如果你已经学过第 50 章的安卓环境或第 60 章的 iOS 环境，这一节是你最该看的一节：把三个平台的环境搭建摆到一张桌子上，看看哪些环节是"移动开发的通用件"，哪些是"鸿蒙自己的脾气"。没学过另外两家的同学也不用跳走，这张表是你将来横向理解三大平台的底片，现在混个脸熟，后面读到对应章节自然会回来对照。

##### 从表里能读出的三件事

第一件：工程骨架是通用件。IDE、语言、构建、清单、签名、日志、模拟器。商店，每个平台都是这八个环节，一个不少。差别只在名字和自动化程度。所以"学第二个移动平台"永远比"学第一个"快得多：你已经知道要装什么、每个环节会出什么类型的错，只是换名字重认一遍。

第二件：鸿蒙多了一个"预览器"环节。安卓和 iOS 都有界面预览能力，但鸿蒙把预览器做成了和模拟器并列的日常入口：写 UI 靠它秒刷，测能力才开模拟器。这个分工本书第一节就点过，放在三平台对照里看更清楚：它是"声明式 UI 普及后，把'看效果'从'跑应用'里拆出来"的产物，SwiftUI 的预览是同一个思路，只是鸿蒙把它提到了更高的地位。

第三件：签名是三个平台里差异最大的环节。安卓最松（debug keystore 自动生成，发布自己管），iOS 最严（证书、描述文件、设备白名单层层设卡），鸿蒙的调试阶段比 iOS 松、比安卓讲究一点，但把流程塞进了 IDE 里自动办，学习阶段的体感反而最轻松。真正比拼复杂度的是发布阶段，那要到第 78 章才见分晓。

##### 错误示范：把对照表当"翻译词典"

错误示范：安卓老手老王拿到这张表，如获至宝，写鸿蒙代码时全程"硬翻译"，Gradle 的配置语法往 hvigor 里搬，Logcat 的 API 名往 hilog 里套，AndroidManifest 的写法往 module.json5 里抄。结果编译器一路飘红，他越改越气，得出结论"鸿蒙难用"。

纠正：对照表的正确用法是"对概念，不对写法"。看表你要建立的是映射关系，"哦，module.json5 就是鸿蒙的清单文件，权限声明应该在它里面"，然后去查清单文件自己该怎么写。第十节给安卓读者的三条忠告，本质上就是在防这个错：表是地图，不是传送门。地图告诉你目的地在哪个方向，路还是要自己走。

##### 场景案例：30 分钟出一份平台评估速写

这张表还有个实用场景：技术选型。想象一个真实任务，技术负责人让你评估"团队要不要投入鸿蒙"，明天要给结论。你按本章流程把环境装好、跑通 Hello 项目，再拿着这张对照表走一遍，30 分钟能交出一份有血有肉的速写：环境搭建成本（一到两个小时，比 iOS 门槛低）；团队学习曲线（前端背景几乎无痛，安卓背景要重学构建与清单细节）；生态成熟度（迭代快、资料新但少，参考第 70 章）。

这种"快速试水再决策"的姿势，比看十篇评测文章都可靠，因为每个结论都出自你亲手跑过的环境。本书的编写思路也是这个：环境搭建章存在的意义，就是给你一个"亲手试"的最低成本入口。

##### 也说说鸿蒙环境的"快"与"险"

对照着看，鸿蒙环境有它明显的"快"：不用 Mac、不用折腾模拟器加速、签名自动化、SDK 随 IDE 预置：四道传统门槛都被削平了，本章开头的"一到两个小时跑通"就是这些削平的总和。

但"险"也要摆在台面上：生态新，意味着教程和问答的存量少，你搜报错时，安卓能翻出十年积累的帖子，鸿蒙很多时候要靠官方文档和社区一手信息，第十一节的自救三步在鸿蒙上因此更重要；API 迭代快，意味着今天装的环境过几个月就可能要按第四节的对齐纪律升一轮。快和险是一体两面：门槛低是因为一切都在快速演进，而快速演进的代价是你得保持跟进。这也是本书反复强调"以官方文档为准"的原因。

这张表还能反过来用，帮你安排后面章节的学习顺序。已经会安卓的同学，读到第 62 章 SwiftUI 时会突然轻松，因为你在第 73 章见过的 ArkUI 换了个语法；先学鸿蒙的同学也一样，第 51 章的 Compose 对你几乎是"复习"。声明式 UI、声明清单、构建系统、日志过滤，这些工序在三大平台之间是可以互相抵扣学分的，所以别问"先学哪个平台好"，先把手头这个学到能跑通，另外两个的下手成本会低到你惊讶。

如果时间只够记一件事，就记这张表的读法：竖着看是"换平台重认一遍名字"，横着看是"同一个环节的三种做法"。读法对了，这张表能陪你读到全书最后一章。
