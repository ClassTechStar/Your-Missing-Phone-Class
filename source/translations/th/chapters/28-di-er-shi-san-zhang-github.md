### บทที่ 23 ภาคผนวก: คู่มือเริ่มต้น GitHub — จากที่เก็บโค้ดสู่แพลตฟอร์มการทำงานร่วมกัน

{class="chapter-intro mb-4"}
บทที่แล้วเราคุยเรื่อง "การคิดแบบโปรแกรมเมอร์" กันไปแล้ว แต่จะเอาแนวคิดนั้นมาลงมือทำจริงและร่วมงานกับคนอื่น ก็ข้ามชื่อหนึ่งไปไม่ได้ นั่นคือ GitHub ไม่ว่าคุณจะเป็นนักศึกษาคอมพิวเตอร์กำลังเตรียมแข่งขัน อยากเก็บผลงานโค้ดของตัวเอง หรือแค่อยากแอบดูว่านักพัฒนาทั่วโลกกำลังเล่นอะไรกันอยู่ GitHub ก็เป็นแพลตฟอร์มที่คุณต้องรู้จัก ในหัวข้อนี้เราจะเริ่มจากคอนเซปต์พื้นฐานที่สุด เพื่อช่วยให้คุณเข้าใจมันได้ชัดเจน

#### หนึ่ง GitHub แท้จริงแล้วคืออะไร?

พูดง่าย ๆ ก็คือ GitHub เป็น <strong>แพลตฟอร์มจัดเก็บโค้ดและทำงานร่วมกัน</strong> ที่สร้างบนพื้นฐานของ Git เปิดตัวปี 2008 และถูกไมโครซอฟต์ซื้อกิจการในปี 2018 ปัจจุบันยังคงเป็นที่เก็บโค้ดโอเพนซอร์สที่ใหญ่ที่สุดในโลก ดูแลรีโปอยู่หลายร้อยล้านแห่ง ครอบคลุมภาษาโปรแกรมกระแสหลักแทบทุกภาษา

ถ้าจะใช้การเปรียบเทียบเพื่อความเข้าใจ ก็คือ:<strong>ถ้า Git คือสมุดบันทึกบนคอมของคุณ GitHub ก็คือแพลตฟอร์มบล็อกสาธารณะ</strong> — คุณเผยแพร่ผลงานของตัวเอง ติดตามโปรเจกต์ของคนอื่น ร่วมพูดคุยและทำงานร่วมกันได้ มันไม่ใช่แค่ "คลังหลังบ้านของโปรแกรมเมอร์" แต่คล้าย "เมืองเทคโนโลยี" ที่นักพัฒนาทั่วโลกร่วมกันสร้าง — โปรเจกต์ถือกำเนิด พัฒนาต่อ ถูกถกเถียง และถูกนำไปใช้ซ้ำที่นี่

สำหรับคนทั่วไป GitHub ก็ไม่ได้ไกลตัวอย่างที่คิด คนที่ไม่ใช่โปรแกรมเมอร์จำนวนมากใช้มันเก็บโน้ต อีบุ๊ก บล็อกส่วนตัว หรือแม้แต่สำรองไฟล์ตั้งค่าต่าง ๆ แค่คุณมีความต้องการนิดหน่อยที่จะ "จัดระเบียบของตัวเองให้เข้าที่แล้วแชร์ออกไป" GitHub ก็คุ้มค่าที่จะรู้จักแล้ว

พูดสั้น ๆ:<strong>Git ดูแล "การบันทึกการเปลี่ยนแปลงอย่างไร" ส่วน GitHub ดูแล "การเปลี่ยนแปลงเก็บไว้ที่ไหนและร่วมงานกันอย่างไร"</strong> Git คือเครื่องมือ ทำงานอยู่บนเครื่องเรา GitHub คือแพลตฟอร์มที่เอารีโป Git ขึ้นคลาวด์ เพื่อความสะดวกในการร่วมมือและโชว์ผลงาน คุณใช้ Git อย่างเดียวโดยไม่ใช้ GitHub ก็ได้ (เช่น ทำเวอร์ชันเก็บโค้ดส่วนตัว) แต่ถ้าใช้ GitHub ต้องใช้ Git แน่นอน (เพราะ GitHub สร้างบนพื้นฐานของ Git นั่นเอง)

#### สาม คอนเซปต์และฟีเจอร์หลักของ GitHub

##### 📁 คอนเซปต์พื้นฐาน

ก่อนลงมือ มาทำความรู้จักคำที่ใช้บ่อยก่อน ไม่อย่างนั้นเปิดหน้า GitHub มาจะงงเป็นไข่แตก:

- <strong>รีโป (Repository หรือ Repo)</strong>: หนึ่งโปรเจกต์ต่อหนึ่งรีโป ข้างในเก็บไฟล์โค้ดทั้งหมด ประวัติเวอร์ชัน และเอกสารของโปรเจกต์นั้น เข้าใจง่าย ๆ ว่าเป็น "โฟลเดอร์โปรเจกต์"
- <strong>คอมมิต (Commit)</strong>: บันทึกการแก้โค้ดหนึ่งครั้ง ทุกคอมมิตมีข้อความอธิบายกำกับว่า "รอบนี้แก้อะไร ทำไมถึงแก้" นี่คือรากฐานที่ทำให้ Git/GitHub "ย้อนเวลา" ได้
- <strong>บรานช์ (Branch)</strong>: เส้นทางพัฒนาที่แตกออกมาจากสายหลัก อย่างเช่นถ้าคุณอยากเพิ่มฟีเจอร์ใหม่ ก็เปิดบรานช์แยกไปพัฒนาคนละทาง พอเสร็จค่อยรวม (merge) กลับเข้าสายหลัก ไม่กระทบใคร
- <strong>โคลน (Clone)</strong>: ก๊อปรีโปบนคลาวด์มาไว้ที่คอมของเราแบบครบชุด จากนั้นก็แก้โค้ดบนเครื่องตัวเองได้เลย
- <strong>พุช (Push) / พูล (Pull)</strong>: Push คืออัปโหลดโค้ดจากเครื่องเราขึ้น GitHub ส่วน Pull คือดาวน์โหลดโค้ดล่าสุดจาก GitHub มาไว้ที่เครื่อง เป็นสองการเคลื่อนไหวหลักที่ทีมใช้ซิงก์โค้ดให้ตรงกัน
- <strong>Pull Request (ย่อว่า PR)</strong>: เมื่อคุณแก้โค้ดบนบรานช์เสร็จและอยากรวมเข้าบรานช์หลัก ก็ยื่น PR เพื่อให้ทีมรีวิวโค้ดก่อนแล้วค่อยรวม นี่คือกลไกหัวใจของการทำงานร่วมกันบน GitHub
- <strong>อิชชู (Issue)</strong>: ใช้จดบั๊ก ฟีเจอร์ที่ขอ และหัวข้ออภิปราย แต่ละ Issue เหมือนกระทู้สนทนาหนึ่งอัน มอบหมายผู้รับผิดชอบหรือติดป้ายกำกับได้
- <strong>Fork</strong>: ก๊อปรีโปของคนอื่นมาไว้ใต้บัญชีของตัวเอง จะแก้อะไรในสำเนาของตัวเองก็ได้อย่างอิสระ ไม่กระทบรีโปเดิม พอแก้เสร็จก็ส่ง PR กลับไปให้ผู้เขียนเดิม ขอให้รวมงานที่เราปรับปรุงเข้าไป

##### 🛠️ ฟีเจอร์หลัก

GitHub ให้มาไม่ใช่แค่ที่เก็บโค้ด แต่ยังรวมถึง:

- <strong>การควบคุมเวอร์ชัน</strong>: บันทึกประวัติการแก้โค้ดทุกครั้ง พอแก้พังเมื่อไรก็ย้อนกลับไปเวอร์ชันปกติก่อนหน้าได้ทันที
- <strong>การทำงานเป็นทีม</strong>: รองรับหลายคนพัฒนาโปรเจกต์เดียวกันแบบขนานกันได้ หลายคนทำพร้อมกันก็ไม่ทับกัน ไม่ชนกัน
- <strong>การติดตามปัญหา</strong>: ใช้ Issue จดบั๊กและคำขอฟีเจอร์ ทำให้ทีมตามงานได้สะดวก
- <strong>การจัดการโปรเจกต์</strong>: มีเครื่องมือจัดการในตัว เช่น สิ่งที่ต้องทำ บอร์ดโปรเจกต์ (Projects) เหมือนมี Trello จิ๋วติดมาให้ด้วย
- <strong>การทำงานอัตโนมัติ</strong>: ผ่าน <strong>GitHub Actions</strong> ทำให้พอคอมมิตโค้ดแล้ว คอมไพล์ ทดสอบ แพ็ก และดีพลอยเองอัตโนมัติ เป็นเครื่องมือหัวใจของแนวคิด "CI/CD (การผสาน/การดีพลอยอย่างต่อเนื่อง)" ยุคใหม่
- <strong>การจัดการเอกสาร</strong>: README แนะนำโปรเจกต์ Wiki เก็บสถาปัตยกรรมละเอียดและข้อตกลงการพัฒนา แถม Pages ยังโฮสต์เว็บสถิตให้ได้เลย
- <strong>การเก็บและโชว์โค้ด</strong>: ทุกรีโปมีหน้าเว็บสวยงามให้ชม ไฮไลต์ไวยากรณ์โค้ดให้ด้วย เป็น "หน้าตา" ของผลงานสายเทคนิคของคุณ
- <strong>ชุมชนโอเพนซอร์ส</strong>: คุณกด Star (เก็บชอบ) โปรเจกต์ที่ชอบ Watch (ติดตาม) ข่าวคราวโปรเจกต์ Follow (ติดตาม) นักพัฒนา แล้วร่วมงานโอเพนซอร์สระดับโลกได้

#### สี่ ลงทะเบียนและเริ่มใช้งาน: สร้างรีโปแรกของคุณใน 5 นาที

##### 📝 ลงทะเบียนบัญชี

1. เปิด <a href="https://github.com" class="text-primary hover:underline" target="_blank" rel="noopener">github.com</a> แล้วกด "Sign up"
2. กรอกอีเมล ตั้งรหัสผ่านและชื่อผู้ใช้ (ชื่อผู้ใช้จะโผล่ในที่อยู่โปรไฟล์ของคุณ แนะนำให้ใช้ภาษาอังกฤษ เช่น <code class="bg-gray-100 dark:bg-gray-800 px-1 rounded">github.com/yourname</code>)
3. ยืนยันอีเมลและผ่านการตรวจสอบว่าไม่ใช่บอท
4. เลือกแพ็กฟรี (Free) ก็พอ สำหรับผู้ใช้ทั่วไปเกินพออยู่แล้ว

##### 📁 สร้างรีโปแรก

1. ล็อกอินแล้วกดปุ่ม "+" มุมขวาบน เลือก "New repository"
2. ตั้งชื่อรีโป (Repository name) เช่น <code class="bg-gray-100 dark:bg-gray-800 px-1 rounded">my-first-project</code>
3. เขียนคำอธิบายสั้น ๆ (Description) ให้คนอื่นรู้ว่ารีโปนี้ไว้ทำอะไร
4. เลือกแบบสาธารณะ (Public) หรือส่วนตัว (Private) รีโปสาธารณะทุกคนเห็น ส่วนตัวเห็นเฉพาะตัวเองกับผู้ร่วมงาน บัญชีฟรีก็ทำรีโปส่วนตัวได้ไม่จำกัด
5. ติ๊ก "Add a README file" — README คือ "คู่มือ" ของโปรเจกต์ แนะนำให้ทุกรีโปควรมี
6. กด "Create repository" เป็นอันจบ รีโป GitHub แรกของคุณถือกำเนิดขึ้นแล้ว!

#### ห้า เวิร์กโฟลว์พื้นฐาน: จากเครื่องเราสู่คลาวด์

หัวใจของเวิร์กโฟลว์ GitHub คือการจำวงจรนี้ให้ขึ้นใจ:<strong>แก้ไฟล์ในเครื่อง → สเตจ → คอมมิต → พุช → คลาวด์อัปเดต</strong> มาอธิบายแต่ละขั้นแบบภาษาคนทั่วไป:

1. <strong>แก้ไฟล์</strong>: เปิดเอดิเตอร์บนคอมเขียนโค้ดหรือแก้เอกสาร
2. <strong>git add</strong>: เพิ่มไฟล์ที่แก้เข้า "พื้นที่สเตจ" เทียบเท่ากับบอก Git ว่า "การแก้พวกนี้ เตรียมบันทึกไว้แล้ว"
3. <strong>git commit</strong>: บันทึกการเปลี่ยนแปลงในพื้นที่สเตจอย่างเป็นทางการเป็น "คอมมิต" หนึ่งครั้ง พร้อมข้อความสั้น ๆ เช่น "แก้บั๊กหน้าล็อกอิน" ขั้นนี้เสร็จอยู่ในเครื่องเราล้วน ๆ
4. <strong>git push</strong>: อัปโหลดคอมมิตจากเครื่องเราขึ้นคลาวด์ GitHub คนอื่นจึงจะเห็นงานได้
5. <strong>git pull</strong>: ก่อนเริ่มทำงาน ดึงโค้ดล่าสุดจากคลาวด์มาก่อน เพื่อให้เครื่องเราตรงกับเพื่อนร่วมทีมเสมอ

สำหรับมือใหม่ จำคำกลอนนี้ไว้:<strong>"พูลก่อนแล้วค่อยแก้ แก้เสร็จก็แอด คอมมิตพร้อมข้อความ สุดท้ายพุชขึ้นคลาวด์"</strong> ฝึกให้เป็นนิสัย ทำงานร่วมกับทีมก็จะไม่ปั่นป่วน

#### หก เวิร์กโฟลว์ทีม: Pull Request ทำงานอย่างไร

จุดแข็งที่สุดของ GitHub คือกลไกการทำงานร่วมกัน เวิร์กโฟลว์ทีมแบบคลาสสิกจะเป็นแบบนี้:

1. <strong>เปิดบรานช์</strong>: แตกบรานช์ใหม่จากบรานช์หลัก (ปกติชื่อ main หรือ master) เช่น <code class="bg-gray-100 dark:bg-gray-800 px-1 rounded">feature/login</code> แล้วพัฒนาฟีเจอร์ใหม่บนบรานช์นี้
2. <strong>พัฒนาและคอมมิต</strong>: เขียนโค้ดบนบรานช์ใหม่ คอมมิตหลายรอบเพื่อจดความคืบหน้า
3. <strong>พุชขึ้น GitHub</strong>: พุชบรานช์ขึ้นรีโปบนคลาวด์
4. <strong>ยื่น Pull Request</strong>: เปิด PR บนหน้าเว็บ GitHub ขอรวมบรานช์ของคุณเข้าบรานช์หลัก เขียนให้ชัดว่า PR นี้แก้อะไรและทำไมถึงแก้
5. <strong>รีวิวโค้ด (Code Review)</strong>: เพื่อนร่วมทีมอ่านโค้ดของคุณ เสนอความเห็นหรือแนะนำให้แก้ คุณคอมมิตต่อตามฟีดแบ็กได้ PR จะอัปเดตเองอัตโนมัติ
6. <strong>รวมโค้ด (Merge)</strong>: รีวิวผ่านแล้ว กด "Merge" รวมโค้ดเข้าบรานช์หลัก ผลงานของคุณเข้าโปรเจกต์อย่างเป็นทางการแล้ว!

เวิร์กโฟลว์นี้รับประกันว่า <strong>โค้ดทุกชิ้นผ่านการรีวิวก่อนเข้าบรานช์หลักเสมอ</strong> ความเสี่ยงพลาดจึงต่ำลงมาก โปรเจกต์โอเพนซอร์สก็ใช้กลไกนี้รับงานจากคนแปลกหน้าทั่วโลก — คุณยื่น PR เข้าโปรเจกต์โอเพนซอร์สดัง ๆ ก็ได้ พอถูกรับ คุณก็กลายเป็นผู้ร่วมพัฒนาโปรเจกต์นั้นแล้ว

#### เจ็ด สถานการณ์ใช้งาน GitHub แบบคลาสสิก

##### 🎓 นักศึกษากับการแข่งขันและโปรเจกต์รายวิชา

นักศึกษาคอมพิวเตอร์ที่ลงแข่ง ACM แฮ็กะธอน หรือทำโปรเจกต์จบ แทบทุกคนต้องพึ่ง GitHub มันทำหน้าที่ทั้งแพลตฟอร์มทำงานร่วมกันของทีม และหน้าต่างโชว์ผลงาน — กรรมการแข่งเปิดดูรีโปของคุณได้ตรง ๆ เห็นทั้งคุณภาพโค้ดและกระบวนการทำงานร่วมกัน หลายบริษัทรับสมัครงานก็ขอลิงก์โปรไฟล์ GitHub มาเป็นหลักฐานฝีมือทางเทคนิคด้วย

##### 📚 คลังความรู้ส่วนตัวและที่เก็บโน้ต

คนที่ไม่ใช่โปรแกรมเมอร์ก็ใช้ GitHub ได้ หลายคนใช้เก็บโน้ตเรียน บล็อกสายเทคนิค (คู่กับ GitHub Pages ทำเว็บได้ฟรี) หรืออีบุ๊ก เขียนด้วย Markdown + จัดเวอร์ชันด้วย Git + สำรองบนคลาวด์ ครบสามอย่างในที่เดียว

##### 🌐 ร่วมพัฒนาโปรเจกต์โอเพนซอร์ส

GitHub คือฐานทัพหลักของกระแสโอเพนซอร์สทั่วโลก คุณ Fork โปรเจกต์ที่ชอบ แก้แล้วส่ง PR กลับคืนชุมชน หรือจะแค่ Star เก็บโปรเจกต์ดี ๆ ไว้ตามอัปเดตก็ได้ การร่วมโอเพนซอร์สเป็นทางที่ดีที่สุดทั้งฝึกฝีมือและสะสมชื่อเสียง

##### 🤖 ดีพลอยอัตโนมัติกับ CI/CD

ด้วยพลังของ GitHub Actions ทำ "พุชโค้ดปุ๊บ ทดสอบเอง + ดีพลอยขึ้นเซิร์ฟเวอร์เอง" แบบอัตโนมัติเต็มระบบได้ บล็อกส่วนตัวหรือเว็บเอกสารจำนวนมากตั้งมาแบบนี้ เขียนบทความเสร็จพุชหนึ่งที เว็บก็อัปเดตเองทันที

##### 💾 สำรองโค้ดและซิงก์หลายเครื่อง

ใช้รีโปโค้ดเป็นคลาวด์ไดรฟ์สิ เปลี่ยนคอม ทำงานหลายเครื่อง เมื่อไรก็ git pull หนึ่งครั้งได้โค้ดล่าสุด ไม่ต้องแบกแฟลชไดรฟ์ก๊อปไปก๊อปมาอีกต่อไป

#### แปด คำแนะนำสำหรับมือใหม่

- <strong>ข้อความคอมมิตต้องเขียนให้ชัด</strong>: อย่าเขียนขี้เรื่องแบบ "update" commit message ที่ดีคือแบบ "แก้ปัญหาผู้ใช้ล็อกอินแล้วเด้งไปหน้าผิด" ผ่านไปครึ่งปีกลับมาอ่านก็ยังรู้ว่าวันนั้นทำอะไรไว้
- <strong>คอมมิตบ่อย ๆ ก้าวเล็กแต่ไว</strong>: ทำฟีเจอร์เล็ก ๆ เสร็จชิ้นหนึ่งก็คอมมิตหนึ่งครั้ง ไม่ใช่เขียนทั้งวันค่อยมาคอมมิตรอบเดียว แบบนี้พอมีปัญหาจะไล่หาต้นตอได้ง่ายกว่า
- <strong>พัฒนาบนบรานช์ อย่าแก้บรานช์หลักตรง ๆ</strong>: แม้จะเป็นโปรเจกต์ส่วนตัว ก็ฝึกเปิดบรานช์ไว้ ต่อให้ต้องทำงานเป็นทีมในอนาคตก็จะไม่งงมืองงเท้า
- <strong>ใช้ .gitignore ให้เป็น</strong>: ไฟล์นี้บอก Git ว่าไฟล์ไหนไม่ต้องเอาเข้าการจัดเวอร์ชัน (เช่น ไฟล์ตั้งค่าที่มีรหัสผ่าน ผลลัพธ์คอมไพล์ โฟลเดอร์ไลบรารี) กันไม่ให้เอาขยะขึ้นไปกองไว้
- <strong>ชมโปรเจกต์โอเพนซอร์สชั้นเลิศให้มากขึ้น</strong>: แวะไปเล่น GitHub Trending ดูโครงสร้างโค้ด วิธีเขียน README และเวิร์กโฟลว์ของโปรเจกต์ดาวเยอะ ๆ เป็นวิธีฟรีที่พัฒนาฝีมือเร็วที่สุดอย่างหนึ่ง
- <strong>ขอ GitHub Student Pack</strong>: ยืนยันสถานะนักศึกษาแล้วจะได้เครดิตใช้เครื่องมือและบริการเสียเงินมากมายฟรี (Copilot โดเมน คลาวด์ ฯลฯ) มูลค่าหลายพันดอลลาร์

- ห้ามคอมมิตรหัสผ่าน คีย์ API สตริงเชื่อมต่อฐานข้อมูล หรือข้อมูลละเอียดอ่อนอื่นขึ้น GitHub เด็ดขาด ยิ่งเป็นรีโปสาธารณะยิ่งอันตราย — พอรั่วไหล เหล่าบอทไต่เว็บจะกวาดไปภายในเสี้ยววินาที ผลที่ตามมาร้ายแรงมาก

#### เก้า สรุป: ทำไมทุกคนควรรู้จัก GitHub

GitHub ไม่ใช่แค่ "เครื่องมือของโปรแกรมเมอร์" อีกต่อไป มันมากกว่านั้น เป็น <strong>วิถีการทำงานแบบยุคดิจิทัล</strong>: การจัดเวอร์ชันทำให้ทุกอย่างย้อนดูได้ กลไกการทำงานร่วมกันทำให้ทีมวิ่งได้เต็มสปีด จิตวิญญาณโอเพนซอร์สทำให้ความรู้ไหลได้อย่างอิสระ แม้คุณไม่เขียนโค้ด การเข้าใจคอนเซปต์อย่าง "คอมมิต บรานช์ รวมโค้ด" ก็ช่วยให้คุณจัดการทุกสิ่งที่ต้อง "แก้ซ้ำ ๆ + คนหลายคนร่วมทำ" ได้ดีขึ้น — ตั้งแต่วิทยานิพนธ์ เอกสาร โน้ต ไปจนถึงแผนงาน

สำหรับนักศึกษาคอมพิวเตอร์ GitHub ยิ่งเป็นทักษะต้องมี: มันคือพอร์ตโฟลิโอ แพลตฟอร์มทำงานร่วมกัน คลังแหล่งเรียนรู้ และ "เรซูเม่" ที่หนักแน่นที่สุดตอนหางานในอนาคต ลงทะเบียนบัญชีให้เร็ว ค่อย ๆ อัปงานรายวิชาและโปรเจกต์เล็ก ๆ ของตัวเองขึ้นไปสะสมทีละนิด อีกไม่กี่ปีคุณจะมีประวัติทางเทคนิคที่ทำให้คนสัมภาษณ์ตาลุกวาว

<i class="fas fa-hands mr-2"></i>มาลงมือกัน: เปิดประสบการณ์แรกกับ GitHub

{class="list-decimal pl-6 mt-1 space-y-1"}
1. ลงทะเบียนบัญชี GitHub แล้วตกแต่งโปรไฟล์ให้ครบ (รูปหน้าปก แนะนำตัว สายเทคนิคที่สนใจ)
2. สร้างรีโปสาธารณะชื่อ <code class="bg-gray-100 dark:bg-gray-800 px-1 rounded">hello-github</code> พร้อมติ๊ก "Add a README file"
3. เข้าไปในรีโป กดปุ่มแก้ไขของ README.md (ไอคอนดินสอ) เขียนแนะนำตัวสั้น ๆ ด้วย Markdown แล้วคอมมิตการเปลี่ยนแปลง
4. ค้นหาคำที่สนใจในแถบค้นหาของ GitHub (เช่น <code class="bg-gray-100 dark:bg-gray-800 px-1 rounded">python-tutorial</code>) แล้ว Star โปรเจกต์ที่ชอบสักสองอัน
5. (ขั้นสูง) ติดตั้ง Git บนคอม โคลนรีโปมาไว้ที่เครื่อง แก้ README แล้วพุชกลับขึ้นคลาวด์ ให้ครบหนึ่งวงจรเวิร์กโฟลว์ "เครื่องเรา → คลาวด์"
