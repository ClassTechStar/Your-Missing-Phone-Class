### 第四十六章：進階之路——從使用者到架構師

{class="chapter-intro mb-4"}
當你掌握了第三十七至四十四章的方法論，能熟練地用 AI 完成專案開發後，下一步是什麼？本章探討從"AI 工具使用者"到"AI 系統架構師"的進階之路。這個階段的關注點不再是"怎麼讓 AI 寫好程式碼"，而是"怎麼讓 AI 更好地融入整個開發流程"。

#### 一、MCP 協議與工具擴充套件

MCP（Model Context Protocol）是 2025 年出現、2026 年逐漸普及的一個開放協議，它定義了 AI 模型與外部工具之間的通訊標準。簡單來說，MCP 讓 AI 能夠"使用工具"——不只生成程式碼，還能執行命令、查詢資料庫、呼叫 API、操作檔案系統。

在 MCP 之前，每個 AI 工具都有自己的工具整合方式，互不相容。MCP 的出現意味著：一個符合 MCP 標準的工具可以被任何支援 MCP 的 AI 工具使用。這大大降低了工具整合的成本，也讓 AI 的能力邊界從"生成文字"擴充套件到了"執行動作"。

對於進階使用者來說，MCP 的意義在於：你可以為 AI 構建定製化的工具能力。比如，如果你的團隊有一套內部的部署系統，你可以寫一個 MCP 工具讓 AI 直接呼叫部署系統，而不需要人工切換到終端操作。這種"AI 呼叫工具"的能力，是 Agentic Engineering 的基礎設施。

#### 二、自定義工作流與 Skills

當你反覆執行某些固定的 AI 程式設計流程時，可以把它們固化成"自定義工作流"或"Skills"。比如，你的團隊可能有一套標準的程式碼審查流程——先檢查安全性，再檢查效能，再檢查可維護性。你可以把這個流程寫成一個 Skill，讓 AI 在每次程式碼審查時自動按這個流程執行。

自定義工作流的核心價值是"一致性"——它確保每次執行都遵循同樣的標準，不會因為對話長短或上下文不同而產生偏差。這對於團隊協作尤其重要：每個成員使用同樣的工作流，產出的程式碼風格和品質標準就會趨於一致。

構建自定義工作流的方法因工具而異。Cursor 支援 Rules 和 Custom Instructions，Claude Code 支援自定義命令，Replit 支援 Runme。但核心思路一樣：把你的最佳實踐"編碼"成 AI 可執行的指令模板。

#### 三、多 Agent 協作模式

到 2026 年，多 Agent 協作開始成為一個熱門話題。它的核心理念是：不只用一個 AI 來完成任務，而是用多個分工不同的 AI 來協作。比如，一個 AI 負責寫程式碼，一個 AI 負責寫測試，一個 AI 負責程式碼審查——它們各司其職，互相檢查。

多 Agent 協作的優勢在於"分工"和"交叉驗證"：每個 Agent 專注於自己的領域，產出品質更高；Agent 之間的交叉檢查可以發現自己可能忽略的問題。但劣勢也很明顯：協調成本高，通訊開銷大，除錯更復雜。

::: div .info-box .rounded-lg .p-4 .mt-4
{class="font-semibold"}
小貼士：一個人也能玩"多 Agent"

{class="mt-1"}
對於個人開發者來說，你不需要搭建複雜的多 Agent 系統——你可以"扮演"不同的角色來模擬多 Agent 協作。比如：先用一個對話讓 AI 寫功能程式碼；然後開一個新對話（提供 CLAUDE.md 上下文），讓 AI"作為程式碼審查者審查這段程式碼"；最後再開一個對話讓 AI"根據審查意見修正程式碼"。這種"一人多角"的方式，能獲得多 Agent 協作的大部分好處，而不需要複雜的基礎設施。
:::

#### 四、持續學習路徑

AI 程式設計是一個快速變化的領域。今天的最佳實踐，明天可能就需要更新。以下是幾條持續學習的建議：

第一，關注源頭而非二手解讀。Andrej Karpathy 的原始推文和 CLAUDE.md、Anthropic 和 OpenAI 的官方檔案、各大工具的更新日誌——這些是第一手資訊。社群文章和教學是對這些資訊的解讀和總結，有價值但可能失真。養成讀原始資料的習慣。

第二，實踐驅動學習。不要"學完再做"，而要"邊做邊學"。每次遇到新的問題型別（比如第一次處理檔案上傳、第一次接入第三方 API），就以此為機會學習相關知識。實踐中的學習效率遠高於脫離場景的理論學習。

第三，保持工具敏感度但不過度追新。每隔一兩個月，花半天時間瞭解最新的工具和趨勢——但不要每次有新工具就切換。判斷標準是：新工具是否能顯著提升你的某個瓶頸？如果不能，當前的組合就夠了。

第四，構建個人知識庫。把你每次解決複雜問題的對話、每次踩坑的教訓、每次有效的方法記錄下來。不需要公開發布——這是你自己的"方法論筆記"。隨著時間積累，它會成為你最寶貴的資產。
