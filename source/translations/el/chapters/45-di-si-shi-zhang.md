### Κεφάλαιο 40: Μηχανική απαιτήσεων — από την ιδέα σε οδηγίες που η AI μπορεί να εκτελέσει

{class="chapter-intro mb-4"}
Αν η μηχανική συμφραζομένων λύνει το «να καταλαβαίνει η AI το πλαίσιο», η μηχανική απαιτήσεων λύνει το «να ξέρει η AI τι ακριβώς πρέπει να κάνει αυτή τη φορά». Εδώ φαίνεται περισσότερο από παντού η διαφορά μεταξύ ανθρώπων στον προγραμματισμό με AI — με τα ίδια εργαλεία και το ίδιο μοντέλο, άλλοι φτιάχνουν εντυπωσιακά projects και άλλοι μόνο μέτρια φτιαγμένα «παιχνιδάκια». Η διαφορά συνήθως δεν είναι στις τεχνικές ικανότητες, αλλά στην ικανότητα να εκφράζει κανείς τις απαιτήσεις του.

#### 1. Από τη θολή ιδέα στη δομημένη απαίτηση

Κάθε project ξεκινά από μια θολή ιδέα — «θέλω να φτιάξω μια εφαρμογή καταγραφής εσόδων-εξόδων», «θέλω μια προσωπική ιστοσελίδα», «θέλω ένα εργαλείο λίστας υποχρεώσεων». Οι ιδέες αυτές δεν έχουν κανένα πρόβλημα καθεαυτές, αλλά αν τις πετάξεις έτσι κι αλλιώς στην AI, η ποιότητα του αποτελέσματος εξαρτάται εντελώς από την τύχη. Στόχος της μηχανικής απαιτήσεων είναι να μετατρέπει αυτή τη θολή ιδέα σε μια δομημένη απαίτηση που η AI μπορεί να εκτελέσει με ακρίβεια.

Τα καλά νέα: για τη δομημένη απαίτηση δεν χρειάζεται να γράψεις PRD δεκάδων σελίδων. Αρκεί να απαντήσεις πέντε ερωτήσεις, που ονομάζουμε «τα πέντε στοιχεία της απαίτησης»:

Τα πέντε στοιχεία της απαίτησης με παραδείγματα

Τα πέντε στοιχεία δεν χρειάζεται να γραφτούν σε επίσημο έγγραφο — αρκεί ακόμα και να τα περάσεις γρήγορα από το μυαλό σου. Το ζητούμενο είναι να αποκτήσεις τη συνήθεια «πρώτα το σκέφτομαι καθαρά, μετά μιλάω». Θα δεις ότι όταν μπορείς να απαντήσεις καθαρά αυτές τις πέντε ερωτήσεις, η περιγραφή των απαιτήσεών σου γίνεται από μόνη της δομημένη.

#### 2. Η τέχνη της στρωματωμένης ανάλυσης των απαιτήσεων

Για μεγαλύτερα projects, μία περιγραφή απαίτησης δεν αρκεί. Χρειάζεται να σπάσεις τη μεγάλη απαίτηση σε μικρές, ανεξάρτητα επαληθεύσιμες υπο-απαιτήσεις. Η διαδικασία αυτή λέγεται «ανάλυση απαιτήσεων», και η βασική της αρχή είναι: κάθε υπο-απαίτηση πρέπει να μπορεί να ολοκληρωθεί, να επαληθευτεί και να παραδοθεί ανεξάρτητα.

Παράδειγμα: για το «φτιάχνω μια προσωπική εφαρμογή καταγραφής εσόδων-εξόδων», ένας λογικός τρόπος ανάλυσης είναι:

1. Υλοποίηση της βασικής λειτουργίας εγγραφών εσόδων-εξόδων (να προσθέτει, να βλέπει, να διαγράφει εγγραφές)·
2. Προσθήκη λειτουργίας κατηγοριών (ετικέτες όπως εστίαση, μετακινήσεις σε κάθε εγγραφή)·
3. Υλοποίηση μηνιαίας σύνοψης (στατιστικά εσόδων-εξόδων ανά μήνα)·
4. Προσθήκη οπτικοποίησης δεδομένων (απεικόνιση της δομής εξόδων με διαγράμματα).

Κάθε βήμα είναι μια λειτουργική βελτίωση που μπορεί να τρέξει και να επαληθευτεί ανεξάρτητα.

:::inline div .quote-line
Ο χρυσός κανόνας της ανάλυσης απαιτήσεων: στο τέλος κάθε βήματος, το έργο πρέπει να είναι "κάτι που δουλεύει"—όσο τραχύ κι αν είναι. Ποτέ μην αφήνεις το έργο σε κατάσταση "όλα στη μέση, τίποτα δουλεύει".
:::

Αυτός ο τρόπος ανάλυσης έχει δύο οφέλη. Πρώτον, σου επιτρέπει να βλέπεις διαρκώς πρόοδο — με κάθε ολοκληρωμένο βήμα η εφαρμογή σου αποκτά μια λειτουργία ακόμα, και αυτή η θετική ανατροφοδότηση είναι ζωτικής σημασίας για projects μεγάλης διάρκειας (όλοι χρειαζόμαστε λίγη αίσθηση επιτυχίας). Δεύτερον, κρατά κάθε εργασία της AI αρκετά μικρή, μειώνοντας τον κίνδυνο «παρανόησης από την AI» — όσο μικρότερη η εργασία, τόσο ακριβέστερη η κατανόηση και τόσο υψηλότερη η ποιότητα του αποτελέσματος.

#### 3. Πρότυπο και πρακτική συγγραφής PRD

Για μεγαλύτερα projects (π.χ. μια full-stack εφαρμογή με frontend και backend και πολλαπλά λειτουργικά modules), τα πέντε στοιχεία μπορεί να μην φτάνουν. Τότε χρειάζεσαι ένα πιο επίσημο έγγραφο απαιτήσεων project (PRD). Ένα σημείο που παρερμηνεύεται εύκολα: το PRD δεν γράφεται για να το διαβάσει η AI — γράφεται για σένα, για να τακτοποιήσεις τη σκέψη σου· μόνο τότε μπορείς να δώσεις στην AI πιο ακριβείς οδηγίες.

Ένα καλό PRD δεν χρειάζεται να είναι μακροσκελές, αλλά πρέπει να περιλαμβάνει έξι μέρη: σύνοψη project (σε μία παράγραφο τι ακριβώς κάνει), λίστα λειτουργιών (τι είναι κάθε σημείο-λειτουργία), τεχνική προσέγγιση (ποιο τεχνολογικό stack, χονδρική αρχιτεκτονική), μοντέλο δεδομένων (οι βασικές δομές δεδομένων), περιγραφή διεπαφής (πώς μοιάζουν οι κύριες σελίδες), πλάνο ανάπτυξης (σε πόσα βήματα ολοκληρώνεται).

::: div .code-block
:::inline div .code-head
<span>PRD.md</span><span class="dots">···</span>
:::

```
# PRD εφαρμογής προσωπικού λογιστηρίου
## Επισκόπηση έργου
Μια ελαφριά εφαρμογή προσωπικού λογιστηρίου, με καταγραφή εσόδων/εξόδων, κατηγορίες, μηνιαία σύνοψη και οπτικοποίηση δεδομένων.
## Λίστα λειτουργιών
1. Καταγραφή εσόδων/εξόδων: ποσό, τύπος (έσοδο/έξοδο), κατηγορία, σημείωση, ημερομηνία
2. Διαχείριση κατηγοριών: έτοιμες οι φαγητό, μετακινήσεις, ψώνια, διασκέδαση, άλλα
3. Μηνιαία σύνοψη: συνολικά έσοδα, έξοδα και υπόλοιπο ανά μήνα
4. Οπτικοποίηση εξόδων: πίτα με τα ποσοστά κάθε κατηγορίας
5. Εξαγωγή δεδομένων: σε CSV
## Τεχνικός σχεδιασμός
- Frontend: React + TypeScript + Tailwind CSS
- Αποθήκευση: localStorage (χωρίς backend)
- Γραφήματα: με Chart.js
- Build: Vite
## Μοντέλο δεδομένων
Record {
  id: string
  amount: number
  type: 'income' | 'expense'
  category: string
  note: string
  date: string  // YYYY-MM-DD
}
## Πλάνο ανάπτυξης
Step 1: βασική καταγραφή (CRUD)
Step 2: διαχείριση κατηγοριών
Step 3: μηνιαία σύνοψη
Step 4: οπτικοποίηση δεδομένων
Step 5: εξαγωγή δεδομένων
```
:::

Πρόσεξε το στυλ συγγραφής αυτού του PRD: σύντομες λίστες και δομημένη μορφή, όχι φουσκωμένα κείμενα. Κάθε σημείο-λειτουργία έχει ξεκάθαρο ορισμό, και το μοντέλο δεδομένων περιγράφεται με απλούς τύπους. Ένα PRD σε αυτό το στυλ όχι μόνο το διαβάζεις εσύ καθαρά, αλλά όταν το δώσεις στην AI, εκείνη κατανοεί με ακρίβεια κάθε σημείο της απαίτησης.

#### 4. Στην πράξη: πλήρης πορεία από την ιδέα στο σχέδιο

Δεν έχει νόημα να μένουμε στα θεωρητικά: ας πάρουμε ένα πλήρες παράδειγμα και ας διανύσουμε όλη τη διαδικασία της μηχανικής απαιτήσεων από την αρχή ως το τέλος. Ας πούμε ότι η ιδέα σου είναι: «θέλω να φτιάξω έναν καταγραφέα μάθησης που να παρακολουθεί τι έμαθα κάθε μέρα».

Πρώτο βήμα: περνάς τα πέντε στοιχεία της απαίτησης.

- Who: προσωπική χρήση.
- What: ένα εργαλείο που καταγράφει τι μελέτησες κάθε μέρα, παρακολουθεί τον χρόνο μελέτης και επιτρέπει ανασκόπηση της προόδου.
- Why: θέλω να αποκτήσω συνήθεια συνεχούς μάθησης και να βλέπω τι έχει συσσωρευτεί.
- How: πρώτα μια web έκδοση, με τα δεδομένα τοπικά στον browser.
- Constraint: ανάπτυξη από το μηδέν, ολοκλήρωση των βασικών λειτουργιών μέσα σε 1 εβδομάδα.

Δεύτερο βήμα: αναλύεις τις απαιτήσεις.

1. Βήμα 1: υλοποίηση της λειτουργίας «καταγραφή εγγραφών μάθησης» (ημερομηνία, περιεχόμενο, διάρκεια)·
2. Βήμα 2: προσθήκη «στατιστικών χρόνου μελέτης» (σήμερα, εβδομαδιαίο σύνολο)·
3. Βήμα 3: υλοποίηση προβολής «ημερολογίου μάθησης» (όπως το γράφημα contributions του GitHub)·
4. Βήμα 4: προσθήκη λειτουργίας «ανασκόπησης μάθησης» (τυχαία εμφάνιση εγγραφών από κάποια προηγούμενη μέρα, για επανάληψη).

Τρίτο βήμα: γράφεις ένα σύντομο PRD. Δεν χρειάζεται να είναι μακρύ — η ανάλυση παραπάνω αποτελεί ήδη το κύριο σώμα του PRD. Το τακτοποιείς σε ένα αρχείο .md, το βάζεις στον ριζικό φάκελο του project, και λειτουργεί ως κοινό σημείο αναφοράς για σένα και την AI.

Τέταρτο βήμα: ξεκινάς την ανάπτυξη του πρώτου βήματος. Η οδηγία προς την AI μπορεί να είναι:

::: div .code-block
:::inline div .code-head
<span>Οδηγίες στο AI</span><span class="dots">···</span>
:::

```
Χρειάζομαι την πρώτη λειτουργία ενός ανιχνευτή μάθησης—καταγραφή μαθημάτων.
Ο χρήστης μπορεί να προσθέσει μια εγγραφή με ημερομηνία, περιεχόμενο και διάρκεια (λεπτά).
Τα δεδομένα αποθηκεύονται σε localStorage.
Frontend με React + TypeScript.
Δώσε πλήρη υλοποίηση.
```
:::

Πρόσεξε τα χαρακτηριστικά αυτής της οδηγίας: περιγράφει μόνο τον στόχο του τρέχοντος βήματος (τη λειτουργία καταγραφής), χωρίς να μπλέκει άλλες λειτουργίες· ορίζει ξεκάθαρα τους τεχνικούς περιορισμούς (React, TypeScript, localStorage)· δίνει αρκετές πληροφορίες ώστε η AI να ξέρει «τι να κάνει» και «πώς να το κάνει», ενώ τη συγκεκριμένη υλοποίηση την αφήνει στην AI να αποφασίσει. Αυτή είναι μια υψηλής ποιότητας οδηγία προγραμματισμού με AI, κατεργασμένη μέσω μηχανικής απαιτήσεων.

Σύνοψη κεφαλαίου

- Τα πέντε στοιχεία της απαίτησης: Who / What / Why / How / Constraint — σκέψου καθαρά πριν μιλήσεις
- Χρυσός κανόνας ανάλυσης απαιτήσεων: μετά από κάθε βήμα το project είναι «κάτι που δουλεύει»
- Το PRD γράφεται για σένα: σύνοψη, λίστα λειτουργιών, τεχνική προσέγγιση, μοντέλο δεδομένων, διεπαφή, πλάνο
- Καλή οδηγία = περιγράφεις μόνο το τρέχον βήμα + ξεκάθαροι περιορισμοί + λες «τι να κάνει», όχι «πώς να το κάνει»
- Πρότυπο πλήρους πορείας: πέντε στοιχεία → ανάλυση → PRD → οδηγία, σε τέσσερα βήματα
:::
