### Κεφάλαιο 68: Ο δρόμος προς την πρόοδο — δι και ώματα, ειδοποιήσεις και σύγχρονη αρχιτεκτονική

{class="chapter-intro mb-4"}
Το να φτιάξεις μια εφαρμογή είναι μόνο η αρχή. Σε αυτό το κεφάλαιο μιλάμε για τα εμπόδια που σου εμφανίζονται στην πορεία από το «ξέρω να φτιάξω» στο «ξέρω να φτιάχνω καλά»: πώς ζητάς δι και ώματα με κομψό τρόπο, πώς στέλνεις ειδοποιήσεις χωρίς να γίνεσαι ενοχλητικός, πώς ανεβάζεις την αρχιτεκτονική ένα επίπεδο ψηλότερα, και — το 2026 — πώς δουλεύεις με AI για να γράφεις κώδικα iOS. Καθένα από αυτά θα το συναντήσεις αμέσως σε πραγματικό έργο.

#### 1. Δικαιώματα: πρώτα χτύπα την πόρτα, μετά μπες

Κάμερα, τοποθεσία, επαφές, ειδοποιήσεις… σε αυτές τις «ευαίσθητες περιοχές» το iOS απαιτεί η εφαρμογή να εμφανίζει pop-up αίτημα στον χρήστη τη στιγμή που χρειάζεται το δικαίωμα. Ο κανόνας είναι τρία βήματα — «δήλωση + αίτημα + κομψή υποβάθμιση»:

::: div .code-block
:::inline div .code-head
<span>SWIFT · Αίτημα δι και ωμάτων (παράδειγμα με τοποθεσία)</span><span class="dots">···</span>
:::

```
// 1. Δήλωση κειμένου χρήσης στο Info.plist (χωρίς αυτό κρασάρει αμέσως!)
// Privacy - Location When In Use Usage Description: "Χρησιμοποιείται για την πρόγνωση της πόλης σου"

// 2. Αίτημα τη στιγμή της χρήσης
import CoreLocation

@Observable
class LocationModel {
    private let manager = CLLocationManager()

    func request() {
        switch manager.authorizationStatus {
        case .notDetermined: manager.requestWhenInUseAuthorization()
        case .denied, .restricted: /* Οδήγησε στις ρυθμίσεις */
        default: /* Εγκρίθηκε, πάμε! */
        }
    }
}

// 3. Σε άρνηση, διαχείριση με χάρη: μήνυμα + μετάβαση στις ρυθμίσεις
// UIApplication.shared.open(URL(string: UIApplication.openSettingsURLString)!)
```
:::

::: div .warning-box .rounded-lg .p-4 .mt-4
{class="font-semibold"}
Προσοχή: Το iOS ρωτά τα δι και ώματα «μία μόνο φορά»

{class="mt-1"}
Το pop-up δι και ωμάτων στο iOS εμφανίζεται μόνο μία φορά — αν ο χρήστης αρνηθεί, δεν θα ξαναεμφανιστεί ποτέ. Άρα: διάλεξε τη στιγμή του αιτήματος να είναι «αυτή ακριβώς που ο χρήστης πρόκειται να το χρησιμοποιήσει» (όχι να πετάξεις ένα σωρό αιτήματα μόλις ξεκινήσει), και το κείμενο να εξηγεί τη χρήση. Η οδηγία στην οθόνη μετά από άρνηση («πήγαινε στις Ρυθμίσεις να ενεργοποιήσεις την τοποθεσία») είναι απαραίτητο πρότυπο — μην αφήνεις τον χρήστη να κολλήσει σε αδιέξοδο.
:::

#### 2. Ειδοποιήσεις: να λες χρήσιμα πράγματα τη σωστή στιγμή

Οι ειδοποιήσεις είναι το κανάλι που φτάνει η εφαρμογή στον χρήστη, και ταυτόχρονα η λειτουργία που ο χρήστης «μπλοκάρει» πιο εύκολα. Το iOS χρησιμοποιεί το framework UserNotifications, και η αποστολή ειδοποιήσεων έχει τρεις κανόνες: στείλε μόνο το χρήσιμο, άφηνε τον χρήστη να τις κλείνει, μην ενοχλείς τα μεσάνυχτα. Βασική χρήση:

::: div .code-block
:::inline div .code-head
<span>SWIFT · Τοπικές ειδοποιήσεις</span><span class="dots">···</span>
:::

```
import UserNotifications

// 1. Αίτημα δι και ώματος ειδοποιήσεων (popup μία φορά)
UNUserNotificationCenter.current()
    .requestAuthorization(options: [.alert, .sound, .badge]) { granted, _ in
        print(granted ? "Εγκρίθηκε" : "Απορρίφθηκε")
    }

// 2. Προγραμματισμός "κάτω 20:00 υπενθύμιση λογιστηρίου"
func scheduleDailyReminder() {
    let content = UNMutableNotificationContent()
    content.title = "Υπενθύμιση λογιστηρίου"
    content.body = "Σήμερα δεν έχεις καταγράψει τίποτα"
    content.sound = .default

    var comps = DateComponents()
    comps.hour = 20
    let trigger = UNCalendarNotificationTrigger(dateMatching: comps, repeats: true)

    let request = UNNotificationRequest(
        identifier: "daily-reminder",
        content: content,
        trigger: trigger
    )
    UNUserNotificationCenter.current().add(request)
}
```
:::

Προσοχή: η άδεια ειδοποιήσεων στο iOS επίσης «εμφανίζεται μία μόνο φορά», και ο χρήστης μπορεί να την κλείσει όποτε θέλει από τις ρυθμίσεις του συστήματος — γι' αυτό είναι σημαντική η αίσθηση αξίας του περιεχομένου των ειδοποιήσεων· μία υπερβολική αποστολή μπορεί να χάσει τον χρήστη για πάντα.

#### 3. Προχωρημένη αρχιτεκτονική: βαθύτερα στο MVVM και η δοκιμασιμότητα

Στο Κεφάλαιο 65 χρησιμοποιήσαμε MVVM· εδώ προσθέτω τρία προχωρημένα σημεία:

- Αφαίρεση με protocols: κάνε το ViewModel να εξαρτάται από protocol και όχι από συγκεκριμένη κλάση — στις δοκιμές μπορείς να «εγχύσεις» ψεύτικη πηγή δεδομένων, αυτό είναι ο θεμέλιος λίθος της δοκιμασιμότητας·
- Ενιαία ευθύνη: κάθε ViewModel αναλαμβάνει μόνο ένα πράγμα (αυτό του βιβλίου εξόδων δεν ασχολείται με τον καιρό)· όταν οι λειτουργίες πολλαπλασιάζονται, χώρισέ το·
- Μην υπερσχεδιάζεις: σε μικρό προσωπικό έργο, «@Observable κλάση + αφαίρεση με protocol» φτάνει και περισσεύει. Τα βαριά αρχιτεκτονικά σχήματα τύπου VIPER ή Clean Architecture, άσε τα για όταν έρθουν η ομάδα και η πολυπλοκότητα να σε βρουν — τα εργαλεία υπηρετούν τον στόχο, δεν είναι για επίδειξη.

::: div .info-box .rounded-lg .p-4 .mt-4
{class="font-semibold"}
Μικρή συμβουλή: το «όφελος του οικοσυστήματος» του SwiftUI

{class="mt-1"}
Το οικοσύστημα iOS έχει ακόμα δύο προχωρημένα «αποκλειστικά» παιχνίδια: τα widgets (WidgetKit) αφήνουν τον χρήστη να βλέπει πληροφορίες χωρίς να ανοίγει την εφαρμογή (το «έξοδα του μήνα» του βιβλίου εξόδων στην αρχική οθόνη), και οι Συντομεύσεις (App Intents) αφήνουν τον χρήστη να καλεί τις λειτουργίες σου με Siri ή αυτοματισμούς. Και τα δύο έχουν επίσημα frameworks, δεν απαιτούν μεγάλο κόστος εκμάθησης, αλλά προσφέρουν τεράστια ώθηση στην εμπειρία χρήστη — αξίζει να τα ξεκλειδώσεις πρώτα στον δρόμο της προόδου.
:::

#### 5. Βασικά σημεία της ταυτόχρονης εκτέλεσης (concurrency) της Swift: @MainActor και Task

Το σύστημα concurrency της Swift 6 έχει δύο κανόνες που ο αρχάριος πρέπει οπωσδήποτε να καταλάβει:

- Η διεπαφή ενημερώνεται μόνο στο κύριο νήμα: τα SwiftUI views είναι από προεπιλογή @MainActor, και οι δικτυακές κλήσεις επιστρέφουν στο κύριο νήμα πριν αλλάξουν την κατάσταση (await MainActor.run { ... } ή σημείωσε το ViewModel ως @MainActor)·
- Οι ασύγχρονες εργασίες διαχειρίζονται με Task: ο τροποποιητής .task { } ξεκινά αυτόματα όταν εμφανίζεται το view και ακυρώνεται όταν εξαφανίζεται — αυτός είναι ο κανονικός τρόπος για να ξεκινήσεις ασύγχρονη εργασία στο SwiftUI· μην ρίχνεις σκέτο Task μέσα στο body χωρίς έλεγχο.

::: div .code-block
:::inline div .code-head
<span>SWIFT · Κανονική ασύγχρονη τεχνική</span><span class="dots">···</span>
:::

```
struct WeatherScreen: View {
    @State private var vm = WeatherViewModel()

    var body: some View {
        Group {
            switch vm.state {
            case .loading: ProgressView()
            case .success(let d): WeatherContent(data: d)
            case .error(let m): Text(m)
            }
        }
        .task {                       // Ξεκινά μόλις εμφανιστεί, ακυρώνεται μόλις φύγει
            await vm.search(city: "Πεκίνο")
        }
    }
}
```
:::

Πίσω από αυτούς τους δύο κανόνες βρίσκεται ο σχεδιασμός «ασφάλειας από data races» της Swift 6 — ο compiler πετάει σφάλμα αμέσως μόλις γράψεις κάτι λάθος, αντί να περιμένει να κρασάρει η εφαρμογή για να το ανακαλύψεις. Τα σφάλματα του compiler δεν είναι γκρίνια — σου μπλοκάρουν τις σφαίρες.

{class="mt-1"}
① Πρόσθεσε στο βιβλίο εξόδων «υπενθύμιση καταγραφής στις 20:00 κάθε μέρα» (άδεια ειδοποιήσεων + τοπικές ειδοποιήσεις)· ② άλλαξε την πηγή δεδομένων του ViewModel σε αφαίρεση με protocol και γράψε ένα unit test που «εγχύει» ψεύτικα δεδομένα· ③ πρόσθεσε ένα widget «έξοδα του μήνα» για την αρχική οθόνη. Μόλις ολοκληρώσεις το τρίο, το έργο σου αποκτά πια επαγγελματική εικόνα.
:::
