### Κεφάλαιο 57: Ο δρόμος προς τα προχωρημένα — δι και ώματα, ειδοποιήσεις και σύγχρονη αρχιτεκτονική

{class="chapter-intro mb-4"}
Το να φτιάχνεις εφαρμογή είναι μόνο η αρχή. Σε αυτό το κεφάλαιο μιλάμε για τα εμπόδια από το «ξέρω να φτιάξω» στο «το φτιάχνω καλά»: πώς ζητάς δι και ώματα κομψά, πώς στέλνεις ειδοποιήσεις χωρίς να γίνεσαι ενοχλητικός, πώς ανεβάζεις την αρχιτεκτονική ένα επίπεδο πιο ψηλά, και — το 2026 — πώς γράφεις κώδικα Android με σύντροφο το AI. Κάθε σημείο θα το συναντήσεις αμέσως σε πραγματικό έργο.

#### 1. Δικαιώματα χρόνου εκτέλεσης: πρώτα χτυπάς την πόρτα, μετά μπαίνεις

Κάμερα, τοποθεσία, επαφές, ειδοποιήσεις… για αυτές τις «ευαίσθητες ζώνες», το Android απαιτεί η εφαρμογή να ζητά δι και ώματα από τον χρήστη κατά την εκτέλεση (από το Android 6). Η σειρά: πρώτα δήλωση (Manifest), μετά αίτημα (κώδικας), και αν ο χρήστης αρνηθεί, κομψή υποβάθμιση. Στο Compose, το πιο ανώδυνο είναι το rememberPermissionState της επίσημης βιβλιοθήκης Accompanist:

::: div .code-block
:::inline div .code-head
<span>KOTLIN · Δικαιώματα χρόνου εκτέλεσης (έκδοση Compose)</span><span class="dots">···</span>
:::

```
// Πρώτα δήλωση στο Manifest:
// &lt;uses-permission android:name="android.permission.CAMERA" /&gt;

@Composable
fun CameraButton() {
    val permission = rememberPermissionState(
        permission = android.Manifest.permission.CAMERA
    )
    Button(onClick = {
        when {
            permission.status.isGranted -&gt; openCamera()
            permission.status.shouldShowRationale -&gt; showExplainDialog()
            else -&gt; permission.launchPermissionRequest()
        }
    }) { Text("Λήψη φωτό") }
}
```
:::

::: div .warning-box .rounded-lg .p-4 .mt-4
{class="font-semibold"}
Προσοχή: τι κάνεις αν απορριφθεί οριστικά;

{class="mt-1"}
Αφού ο χρήστης τσεκάρει «μην ξαναρωτήσεις», το launchPermissionRequest δεν βγάζει ξανά παράθυρο. Τότε πρέπει να καθοδηγήσεις τον χρήστη να το ενεργοποιήσει χειροκίνητα στις Ρυθμίσεις (με Intent στη σελίδα ρυθμίσεων της εφαρμογής), και να εξηγήσεις στη διεπαφή «σε τι χρησιμεύει αυτό το δικαίωμα». Με καλύτερη στάση, η διάθεση του χρήστη να δώσει το δικαίωμα ανεβαίνει αισθητά — το κείμενο του αιτήματος δι και ώματος αξίζει να γραφτεί σοβαρά.
:::

#### 2. Ειδοποιήσεις: να λες χρήσιμα πράγματα τη σωστή στιγμή

Οι ειδοποιήσεις είναι το κανάλι που φτάνεις τον χρήστη, αλλά και η λειτουργία που πιο εύκολα «μπλοκάρει». Τρεις κανόνες για ειδοποιήσεις: μόνο χρήσιμες, να μπορεί ο χρήστης να τις κλείσει, καμία ενόχληση τα μεσάνυχτα. Βασική χρήση:

::: div .code-block
:::inline div .code-head
<span>KOTLIN · Αποστολή ειδοποίησης</span><span class="dots">···</span>
:::

```
// Android 13+ απαιτεί πρώτα αίτημα δι και ώματος POST_NOTIFICATIONS (βλ. προηγούμενο κεφάλαιο)

// 1. Δημιουργία καναλιού ειδοποιήσεων (απαιτείται σε Android 8+)
val channel = NotificationChannel(
    "reminder", "Υπενθύμιση", NotificationManager.IMPORTANCE_DEFAULT
)
val manager = getSystemService(NotificationManager::class.java)
manager.createNotificationChannel(channel)

// 2. Αποστολή ειδοποίησης
val notification = NotificationCompat.Builder(this, "reminder")
    .setSmallIcon(R.drawable.ic_notification)
    .setContentTitle("Υπενθύμιση λογιστηρίου")
    .setContentText("Σήμερα δεν έχεις καταγράψει τίποτα")
    .setPriority(NotificationCompat.PRIORITY_DEFAULT)
    .build()
if (ActivityCompat.checkSelfPermission(this,
        Manifest.permission.POST_NOTIFICATIONS) == PackageManager.PERMISSION_GRANTED
) {
    manager.notify(1, notification)
}
```
:::

Προγραμματισμένες εργασίες (π.χ. «κάθε μέρα στις 20:00 υπενθύμιση για καταγραφή») με το WorkManager — είναι ο επίσημα προτεινόμενος «οικοδεσπότης χρονοδιαγράμματος παρασκηνίου»: εξασφαλίζει ότι η εργασία εκτελείται στην κατάλληλη στιγμή, χωρίς εσύ να ασχολείσαι με βελτιστοποίηση μπαταρίας. Για ανάγκες τύπου ξυπνητήρι, με αυτό δεν κάνεις λάθος.

#### 3. Προχωρημένη αρχιτεκτονική: dependency injection και ενότητες (modules)

Όταν το έργο μεγαλώσει, δύο «γλυκά προβλήματα» θα σου χτυπήσουν την πόρτα:

- Χαμός στη δημιουργία αντικειμένων: κάθε οθόνη φτιάχνει μόνη της βάση δεδομένων, API — με το Hilt (framework dependency injection) τα διαχειρίζεσαι ενιαία: «όποιος χρειάζεται κάτι, ανοίγει το στόμα και κάποιος του το φέρνει»·
- Ο κώδικας σωρεύεται σε βουνό: το έργο με ένα μοναδικό module γίνεται όλο και πιο αργό στις αλλαγές — σπά’ το σε πολλά modules (app / core / feature-xxx), και κάθε λειτουργία να αναπτύσσεται και να δοκιμάζεται ανεξάρτητα.

::: div .info-box .rounded-lg .p-4 .mt-4
{class="font-semibold"}
Συμβουλή: μην κάνεις υπερσχεδιασμό

{class="mt-1"}
Το Hilt και η ενότητα-ποίηση είναι καλά εργαλεία, αλλά σε μονοπρόσωπο έργο μην βιάζεσαι. Το βιβλίο εξόδων με ένα module + χειροκίνητη δημιουργία εξαρτήσεων αρκεί πλήρως. Όταν ο κώδικας ξεπεράσει τις δεκάδες χιλιάδες γραμμές, η μεταγλώττιση αρχίσει να αργεί και μπουν πολλοί στη συνεργασία, τότε τα εισάγεις κατ’ ανάγκη. Τα εργαλεία υπηρετούν τον στόχο, δεν είναι για επίδειξη — αυτή είναι και η αρχή «πρώτα η απλότητα» του βιβλίου μας για προγραμματισμό με AI.
:::

#### 5. Βελτιστοποίηση απόδοσης Compose και εργαλεία αποσφαλμάτωσης

Το Compose είναι ευχάριστο στο γράψιμο, αλλά οι «υπερβολικές αναδημιουργίες (recompositions)» φέρνουν κόλλημα. Τρεις πρακτικές τεχνικές:

- Σταθερές παράμετροι: πρόσθεσε @Immutable στα data classes ή χρησιμοποίησε derivedStateOf, ώστε άσχετες αλλαγές κατάστασης να μην προκαλούν μαζικές αναδημιουργίες·
- Μην ξεχνάς το key: το items(list, key = { it.id }) κάνει τη λίστα, σε προσθήκες/διαγραφές, να «αγγίζει» μόνο τα στοιχεία που πρέπει — χωρίς key, μια διαγραφή μπορεί να ξαναζωγραφίσει όλη τη λίστα·
- Η λειτουργία Compose του Layout Inspector: βλέπεις σε πραγματικό χρόνο πόσες φορές αναδημιουργείται κάθε Composable — με μια ματιά φαίνεται ποιος αναδημιουργείται συχνά, και βελτιστοποιείς κατά τα hot spots.

Επίσης άνοιξε τις αναφορές του μεταγλωττιστή Compose (Metrics) για να παίρνεις λίστα «ποια components είναι ασταθή» — στον δρόμο προς τα προχωρημένα, τα δεδομένα είναι πάντα πιο αξιόπιστα από την αίσθηση.
